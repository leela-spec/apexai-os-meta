# 0. How to use this plan

This document is intentionally organized as **one chapter per pipeline stage**. An execution AI should not load all research and all implementation history at once.

For a given stage:

1. read the macro architecture once at run start;
2. read the chapter for the current stage;
3. read the previous stage handoff and the exact input artifacts named by that chapter;
4. inspect only the component-registry entry and code files that own that stage;
5. implement/run/test the stage;
6. write the stage outputs and a compact handoff;
7. move to the next chapter with a fresh/compacted working context.

Do not use chat memory as pipeline state.

## 0.1 Canonical run layout

Use one run root per actual source execution:

```text
artifacts/transcript_pipeline_v2/runs/<run_id>/
  request.json
  source/
  asr/
  alignment/                 # only when S3 runs
  ttk/                       # canonical TTK run directory
  preextract/                # only when S6 runs
  advisory/                  # S10 sidecars
  evaluation/                # S14 product/stage scorecards
  handoffs/
    S00.yaml
    S01.yaml
    ...
```

Do not duplicate TTK's own packet/result/state tree outside `ttk/` merely for presentation.

## 0.2 Lightweight stage handoff shape

Each stage writes a compact YAML/JSON handoff. It is a context boundary, not a second workflow engine.

```yaml
stage: S02
status: PASS|FAIL|BLOCKED|SKIPPED_CONDITIONAL
inputs:
  - path: ...
    sha256: ...
component:
  id: asr_faster_whisper
  version: ...
  config: ...
outputs:
  - path: ...
    sha256: ...
important_result: ...
limitations: []
next_stage: S03
```

Only fields that can be observed should be populated. Do not fabricate measurements.

## 0.3 Context rule for semantic stages

The coding/orchestration AI is **not** the semantic worker.

When S7, S11, or S12 requires strong semantic reasoning, the implementation launches a real allowed subscription CLI subprocess. Trial-1 allowed transports are:

- Claude Code CLI;
- Codex CLI using ChatGPT-plan authentication;
- Antigravity CLI only after a real headless `agy` subprocess smoke passes.

The internal coding agent, an internal subagent, regex, templates, or a Python pseudo-model cannot stand in for these CLIs.

# S0 — Trigger and run initialization

## Goal

Turn an APEX/OpenClaw event, URL, local media path, or transcript-only input into one explicit run request with a stable run identity.

## Input contract

At least one source locator:

```yaml
source:
  type: youtube_url|media_file|transcript_file|watchlist_event
  locator: <url-or-path>
requested_mode: full_audio_to_knowledge|transcript_to_knowledge
```

Optional operator parameters may include language hint, force-fresh acquisition, or benchmark source ID.

## Recommended implementation

**Tool/owner:** thin deterministic Python/PowerShell runner, later invoked by APEX/OpenClaw.

The runner should:

1. create `run_id`;
2. create the run directory;
3. normalize the incoming request into `request.json`;
4. record the starting repository commit and source locator;
5. select the next required stage based on input type, not conversation memory.

Do not put semantic logic here. Do not create another workflow engine.

## Minimal code to inspect

- `scripts/transcript_pipeline_v2/runner.py`
- existing APEX/OpenClaw invocation seam only when integrating the finished standalone path.

## Test

Run at least:

1. URL input -> request created;
2. local media input -> request created;
3. transcript input -> S1/S2 can be bypassed intentionally;
4. rerunning the same request does not silently overwrite a different run.

## Output contract

`<run>/request.json` containing run ID, source locator/type, requested mode, creation time, repo commit, and optional benchmark ID.

## Handoff to S1

S1 receives only `request.json` and the source locator. If input is an existing transcript and mode is `transcript_to_knowledge`, hand off directly to S4 with explicit bypass metadata.

# S1 — Source acquisition and audio materialization

## Goal

Acquire a **real local source artifact** and preserve enough source metadata to identify what was processed.

## Input contract

`request.json` with URL or local media locator.

## Recommended implementation

**Core tools:** existing P1 acquisition path + `yt-dlp` + `ffmpeg`.

For remote media:

1. use the existing P1 downloader rather than inventing a new downloader abstraction;
2. acquire an audio-capable stream;
3. materialize/normalize audio through ffmpeg as required by the ASR path;
4. preserve source URL/ID/title/duration where available;
5. hash the actual local audio/media file.

For a local media file:

- do not redownload;
- normalize only if ASR requires it;
- preserve original file hash plus normalized-audio hash if both exist.

## What must not happen

- Do not generate arbitrary bytes and call them fresh audio.
- Do not copy an old transcript and call that source acquisition.
- Do not use transcript-only services as a substitute for a fresh audio benchmark.

## Minimal code/context to inspect

- `.claude/skills/SourceTranscriptionAnalysisPipeline/**` acquisition scripts actually used today;
- relevant `source_existing` component-registry entry;
- no unrelated semantic/evaluation files.

## Test

On one real source:

- acquisition command exits successfully;
- resulting audio exists and has non-zero realistic media size/duration;
- ffmpeg/decoder can open it;
- SHA-256 is stable on reread;
- source ID/URL in metadata matches the intended source.

For fresh E2E testing, confirm the newly materialized audio artifact was created for the current run.

## Output contract

```text
<run>/source/source-metadata.json
<run>/source/audio.<ext>
```

Metadata includes at minimum source locator/ID, acquisition method, audio path, file SHA-256, duration if available, and creation time.

## Handoff to S2

S2 receives the local audio path plus `source-metadata.json`. It does not need downloader logs unless acquisition failed.

# S2 — Automatic speech recognition

## Goal

Produce an accurate EN/DE transcript with timestamps and acoustic diagnostics good enough to support trustworthy downstream knowledge extraction.

## Input contract

- local audio file from S1;
- source metadata;
- optional language hint/domain hotwords.

## Recommended implementation

### Reference production implementation

Use **faster-whisper** with a calibrated model/configuration, preserving:

- segment start/end;
- word start/end when available;
- word probability;
- average log probability;
- no-speech probability;
- compression ratio;
- temperature/decoding metadata where exposed;
- Silero VAD configuration;
- hotwords where a known source/domain vocabulary justifies them.

Do not strip this telemetry before TTK ingestion if the richer JSON form can preserve it.

### Required bounded challenger before ASR freeze

Run **NVIDIA Parakeet TDT 0.6B v3** on the same difficult EN/DE gold slices in an isolated environment. Parakeet is a stage-local challenger; it does not require rerunning the entire knowledge pipeline to decide whether its transcript quality is better.

### Selection rule

Choose the smallest/fastest local ASR configuration that clears the knowledge-quality-relevant gate. If Parakeet materially improves German/domain vocabulary, numbers, or timestamps at acceptable runtime/integration cost, promote it at S2 only.

## Environment rule

Keep heavy ASR runtimes isolated. Do not force faster-whisper, Parakeet/NeMo/Transformers, WhisperX, and all auxiliary models into one Python environment.

## Test

Use the same manually checked difficult slices for every candidate. Measure where reference labels exist:

- normalized WER or targeted word accuracy;
- proper names/companies;
- numbers/percentages;
- scientific terminology;
- Elliott Wave vocabulary;
- German finance terminology;
- timestamp presence/quality;
- runtime;
- peak memory if practical.

Do not repair transcript text with a semantic LLM as the first response to ASR errors. Re-run the acoustic model/configuration or escalate to the challenger.

## Output contract

```text
<run>/asr/transcript.json
<run>/asr/transcript.srt
<run>/asr/asr-metadata.json
```

`transcript.json` is the richest canonical ASR output and should preserve segment/word timing and diagnostics.

## Handoff to S3

S3 receives audio + chosen ASR transcript. If no alignment/diarization requirement exists, explicitly bypass S3 and hand the chosen transcript to S4.

# S3 — Conditional alignment and speaker attribution

## Goal

Improve `who said what/when` provenance only where that information materially matters.

## Input contract

- S2 transcript;
- source audio;
- source classification: single-speaker vs multi-speaker / interview.

## Recommended implementation

**Tool:** WhisperX for forced alignment; WhisperX + pyannote diarization only when speaker attribution is valuable.

Default behavior:

- single-speaker source with adequate timestamps -> `SKIPPED_CONDITIONAL`;
- multi-speaker interview or timing-sensitive source -> benchmark/run WhisperX.

Do not write custom alignment or diarization code.

## Implementation details

Preserve the S2 transcript as evidence. Alignment/diarization should enrich timing/speaker metadata, not silently rewrite semantic transcript content.

Where diarization yields anonymous speaker IDs, preserve them as IDs; do not invent real person names without separate evidence.

## Test

On the Huberman/Adolphs source or another clearly multi-speaker fixture:

- check a manually reviewed slice for speaker-switch accuracy;
- check word/segment alignment around turns;
- inspect overlap/failure zones;
- measure runtime/dependency burden.

Promote WhisperX as a conditional production stage only if the provenance benefit is material.

## Output contract

Either:

```text
<run>/alignment/alignment.json
<run>/alignment/speaker-segments.json
```

or a compact bypass handoff stating S2 timing is sufficient.

## Handoff to S4

S4 receives the chosen transcript representation plus optional alignment/speaker sidecar. It does not receive WhisperX model/debug context.

# S4 — TTK canonical evidence custody

## Goal

Create immutable transcript/source identity, canonical segments, stable IDs, and file-based state.

## Input contract

- chosen transcript from S2/S3;
- source metadata;
- optional alignment/speaker sidecar.

## Recommended implementation

**Tool/owner:** existing TTK core.

Use TTK initialization rather than creating a new database or generic document store.

Conceptual command:

```powershell
python .claude/skills/transcript-to-knowledge/scripts/ttk.py init <transcript> --output <run>/ttk
```

Extend import only if needed to preserve richer word/acoustic metadata without weakening existing source semantics.

## Invariants

TTK owns:

- source SHA-256;
- canonical segment IDs;
- timestamps;
- core source text;
- file-based state;
- later packet hashes and stale detection.

LangExtract source spans do **not** replace TTK custody.

## Test

- same source input produces stable canonical source identity;
- every source segment has stable ID and text/timing where available;
- no content is silently dropped because an ASR confidence heuristic looked suspicious;
- changed transcript hash causes downstream state to become stale rather than silently reused.

## Output contract

The canonical TTK source/state files inside `<run>/ttk/`.

## Handoff to S5

S5 receives the TTK run directory only. It should not need raw acquisition or ASR logs to construct windows.

# S5 — TTK bounded processing windows

## Goal

Convert canonical transcript segments into bounded semantic-work packets while preserving exact coverage and context/evidence separation.

## Input contract

TTK canonical source/state from S4.

## Recommended implementation

**Tool:** TTK windowing.

Reference behavior:

- approximately 700–1500 words per processing window;
- pause/lexical boundaries where useful;
- one or more neighboring context segments as `context_only`;
- stable packet/window IDs and packet hash;
- exact core coverage across the source.

Processing windows are transport units, **not semantic chapters**.

## Test

- every canonical core segment appears in exactly the intended coverage set;
- context-only segments cannot be cited as evidence;
- packet hashes are stable for unchanged inputs;
- long source creates all expected early/middle/late windows;
- no arbitrary fixed Meso grouping is derived here.

## Output contract

```text
<run>/ttk/work/packets/map/window-0001.json
...
```

Each packet contains source/run identity, packet hash, core segments, and context-only halo.

## Handoff to S6/S7

S6 may consume one packet to create hints. S7 always consumes the original TTK packet; hints are optional augmentation, never a replacement.

# S6 — Optional cheap local pre-extraction

## Goal

Determine whether a small specialist model can cheaply supply useful entities/relations/classification hints without replacing semantic reasoning.

## Input contract

One TTK Map packet from S5.

## Recommended implementation

**Primary challenger:** GLiNER2 in its own isolated environment.

Allowed hint categories include things such as:

- person;
- organization/company;
- product/technology;
- financial instrument;
- candidate relations or narrow structured labels.

Forbidden authority roles:

- thesis selection;
- real Meso boundaries;
- nuanced mechanism interpretation;
- source-support verdict;
- final claim formulation;
- Macro synthesis.

**NuExtract** is a second-wave challenger only if GLiNER2 fails the useful pre-extraction role and multilingual schema extraction remains a demonstrated need.

## Test

Against manually reviewed representative windows:

- entity precision/recall;
- false-hint rate;
- German vs English behavior;
- runtime;
- strong-AI token/quota delta when hints are included;
- change in Map insight recall/quality.

If hints add noise or no material savings, production S6 is a bypass.

## Output contract

Optional sidecar:

```text
<run>/preextract/window-0001.json
```

The sidecar must be clearly labeled `advisory_hints`, with the source packet hash it was derived from.

## Handoff to S7

S7 receives the original TTK packet and, only if S6 is active, the matching hint sidecar.

# S7 — Grounded semantic Map extraction

## Goal

Extract the valuable semantics from each bounded source window with high recall and real source grounding.

## Input contract

- one TTK Map packet;
- optional S6 hints bound to the same packet hash;
- TTK Map semantic contract/schema.

## Recommended implementation

### Recommended route: LangExtract + real subscription CLI provider adapter

Use **LangExtract** for grounded structured extraction/source-location handling, connected through its documented custom-provider mechanism to a **real allowed subscription CLI process**.

Preferred semantic transport for the first working route:

1. Claude Code CLI when installed/authenticated and real subprocess execution works;
2. Codex CLI fallback/control;
3. Antigravity `agy` only after its own real headless subprocess smoke passes.

The LangExtract adapter is a bounded provider seam. Do not fork LangExtract core unless its supported provider mechanism is genuinely insufficient.

Translate LangExtract source locations back into TTK canonical segment IDs/spans. TTK remains provenance authority.

### Required control route: direct CLI Map

Keep one direct CLI Map route:

```text
TTK packet -> real CLI -> TTK Map JSON
```

This is the comparison/control and the production fallback if LangExtract adds no material value or cannot use Trial-1 CLI transport cleanly.

### Semantic responsibility

The strong model owns:

- important themes/subtopics;
- claims and epistemic claim type;
- mechanisms/protocols/arguments;
- source-support interpretation;
- important uncertainty/corrections/caveats;
- entities/concepts where semantically useful.

Do not force field quotas. Empty arrays are valid.

## Prompt/content rules

- core segments may be evidence;
- context-only is understanding only;
- processing window is not a chapter;
- factual/testable claims require exact source evidence;
- preserve contradictions and uncertainty;
- extract distinct valuable semantics, not every sentence;
- do not turn transcript sentences mechanically into claims.

## Test

First use a **single representative packet**, inspect the produced content itself, and reject the route before scale-up if it is generic, wrong-source, sentence-dumping, or semantically shallow.

Then compare representative windows across EN/DE and early/middle/late source positions for:

- important-insight recall;
- factual grounding precision;
- claim-type quality;
- mechanism/argument capture;
- uncertainty preservation;
- source-span correctness;
- token/quota use;
- runtime;
- adapter complexity.

If LangExtract cannot use an allowed CLI transport without disproportionate work, mark it `BLOCKED_FOR_TRIAL1`; use direct CLI. Never create a fake local imitation.

## Output contract

Raw semantic result in exact `ttk.map-result.v2` shape at the TTK expected result path.

## Handoff to S8/S9

S8 handles structured-output/retry at the invocation seam. S9 validates the resulting TTK Map result against the original packet.

# S8 — Structured output and bounded retry

## Goal

Make semantic worker output mechanically consumable without turning schema compliance into a substitute for semantic quality.

## Input contract

- Map or Reduce request;
- corresponding JSON schema/TTK contract;
- real CLI output.

## Recommended implementation

Use **native CLI schema controls first** where available:

- Claude `--json-schema` when supported by the installed CLI mode;
- Codex `--output-schema` when using Codex;
- deterministic JSON/schema validation after process output.

TTK validation remains authoritative for pipeline-specific invariants.

**Instructor/Pydantic** is a conditional challenger only if native schema/retry logic becomes duplicated, brittle, or insufficient across selected providers. Do not insert it solely because it exists.

## Retry policy

Keep retry bounded:

1. initial real semantic call;
2. if process/JSON/schema/TTK validation fails, one retry with the exact machine error and original packet;
3. if still invalid, fail the packet/stage truthfully.

Never replace failure with regex/template output.

## Test

- real valid CLI output parses;
- nonzero subprocess exit does not create a semantic PASS result;
- invalid JSON gets one bounded retry;
- invalid schema gets one bounded retry;
- TTK invariant error is surfaced precisely;
- retry does not change source/packet identity.

## Output contract

A schema-valid semantic candidate plus minimal invocation metadata sufficient to identify the real process/provider and output file.

## Handoff to S9

S9 receives candidate Map files and their original packets; semantic process debug logs are not required unless validation fails.

# S9 — Deterministic Map validation and evidence ledger construction

## Goal

Accept only current, source-grounded Map outputs and build the compact validated evidence input for global synthesis.

## Input contract

- TTK Map packet(s);
- S7/S8 Map result(s).

## Recommended implementation

**Tool:** existing TTK validators + `make-reduce`.

Validate mechanics such as:

- result/packet identity and hash freshness;
- cited segment existence;
- core-only evidence rules;
- exact quote/span existence where required;
- complete window coverage;
- schema/enum/reference integrity;
- stale result rejection.

Do **not** infer semantic `SUPPORTED` merely because a quote exists.

Once all required Map outputs are valid, create the compact Reduce packet/evidence ledger from the validated results.

## Test

At minimum:

- invented quote fails;
- factual claim without required exact evidence fails;
- context-only citation fails;
- stale packet hash fails;
- non-factual object with valid provenance and no forced quote passes where the V2.1 contract permits it;
- missing window prevents complete Map state;
- valid Map set creates Reduce packet without rereading raw full transcript.

## Output contract

- validated TTK Map state;
- TTK Reduce packet / compact evidence ledger.

## Handoff to S10/S11

S10 receives factual claim/evidence pairs for advisory checks. S11 receives the validated compact Reduce packet plus any advisory warning sidecar.

# S10 — Source-support advisory checks

## Goal

Use cheap independent models as warning sensors for possible entailment/factual-consistency mistakes without making them semantic authority.

## Input contract

For selected Map/Reduce factual candidates:

```text
premise = exact source evidence/context
hypothesis = semantic claim/proposition
```

## Recommended implementation

### Multilingual advisory

Benchmark **mDeBERTa NLI** for entailment / neutral / contradiction across EN and DE.

### English comparator

Optionally benchmark **Vectara HHEM** on English factual consistency.

The strong semantic worker remains the source-support authority. Advisory scores may flag a claim for review/retry; they do not silently rewrite `source_support`.

## Test

Use a human-reviewed subset of the support-pair fixture containing:

- supported;
- partial;
- ambiguous;
- unsupported/overreaching examples;
- both English and German for mDeBERTa.

Measure useful precision/recall for **warnings**, not merely raw model accuracy.

If the advisory layer does not catch useful errors or generates too many false alarms, remove it from production while retaining it as an evaluator if useful.

## Output contract

```text
<run>/advisory/source-support.json
```

Each record references claim ID/source evidence and contains model score/class plus `advisory_only: true`.

## Handoff to S11

S11 may receive advisory warnings as additional context. It must receive the validated TTK Reduce packet regardless of whether S10 is active.

# S11 — Global Reduce and knowledge synthesis

## Goal

Transform the complete validated evidence ledger into a useful global knowledge model: Macro thesis, real semantic Meso modules, and refined Micro claims.

## Input contract

- TTK Reduce packet / validated evidence ledger;
- optional S10 advisory warnings;
- Reduce semantic contract/schema.

The semantic worker must **not** reread the raw full transcript independently. Global synthesis is based on the validated evidence ledger.

## Recommended implementation

### Reference/recommended route

Use a **real allowed subscription CLI** directly for Reduce.

The strong model decides:

- global thesis;
- semantic Meso boundaries independent of window boundaries;
- refined/deduplicated Micro claims;
- important mechanisms/protocols/arguments;
- contradictions/corrections/caveats;
- source-support interpretation where refinement is needed;
- useful compression.

### Bounded challenger

Benchmark a **fixed DocETL** Reduce/orchestration route with optimizer **off** first and the same validated evidence where feasible.

Trial 1: DocETL strong-AI calls must go through an allowed subscription CLI adapter. If that is not practical, mark the experiment `BLOCKED_FOR_TRIAL1`; do not use an API.

Only promote DocETL if it materially improves semantic recall/quality, recovery/orchestration, or removes enough custom semantic-dispatch code to justify it.

## Product-level test

Inspect the actual Reduce/wiki content, not only schema status.

Reject output that shows:

- wrong-source content;
- generic “this extraction summarizes…” thesis;
- fixed time/window quartiles as Meso chapters;
- collapse of important later-window insights;
- loss of disagreement/uncertainty;
- every claim marked supported without nuance;
- obvious cross-source contamination;
- low-value sentence restatement instead of synthesis.

On benchmark cases, score:

- Macro usefulness;
- Meso coherence;
- important insight recall;
- Micro grounding;
- uncertainty preservation;
- operator time-to-understand;
- token/quota/runtime.

## Output contract

TTK `reduce-result.v2` at the canonical TTK result path.

## Handoff to S12

S12 receives the validated Reduce result only through the TTK verification queue generated from it.

# S12 — Selective external factual verification

## Goal

Verify consequential/checkworthy factual claims against external evidence without turning the entire pipeline into a research agent.

## Input contract

TTK-generated verification queue containing only claims that meet the V2.1 factual/checkworthiness policy.

Non-factual opinions, recommendations, predictions, anecdotes, decisions, and other non-checkworthy content are not externally verified by default.

## Recommended implementation

**Routing authority:** TTK `make-verify`.

**Trial-1 semantic/research transport:** an allowed subscription CLI with its real research/search tools:

- Claude Code CLI WebSearch/WebFetch where available;
- Codex CLI web-search capability where available;
- Antigravity CLI tooling only if headless smoke passed and the tooling is actually usable.

No browser AI or pay-as-you-go API fallback in Trial 1.

Prefer primary/official sources for factual verification.

If external evidence is insufficient, `UNVERIFIED` is a correct output.

## Test

- only intended factual/checkworthy claims enter queue;
- opinions/predictions do not get automatically researched;
- a decisive external verdict contains actual supporting evidence/source references;
- insufficient evidence returns `UNVERIFIED` rather than hallucinated certainty;
- source support remains separate from external verdict.

## Output contract

Canonical TTK verification result file(s), with evidence references and explicit verdicts.

## Handoff to S13

S13 receives validated Reduce state plus verification results/state. It does not need live browser/search context.

# S14 — Product evaluation, local component selection, and production handoff

## Goal

Judge whether the pipeline produced the intended product and decide any stage-local challenger promotions without letting shallow automation override obvious product failure.

## Input contract

- compiled knowledge product;
- canonical TTK source/Map/Reduce/verify artifacts;
- stage handoffs;
- benchmark gold slices/checklists where relevant;
- outputs from bounded challenger runs.

## Evaluation layers

### 1. Deterministic provenance/integrity

Use TTK/harness mechanics for exact facts such as:

- source identity;
- packet freshness;
- exact quote/span presence;
- full window coverage;
- valid references;
- resume state.

These checks cannot prove semantic quality.

### 2. Human/source-grounded semantic quality

Primary product questions:

- Did the artifact capture the important ideas?
- Is the Macro genuinely informative?
- Are Meso modules real semantic groupings?
- Are Micro factual claims source-faithful?
- Are important mechanisms/arguments/protocols preserved?
- Are uncertainty/corrections/contradictions preserved?
- Is the output source-specific rather than boilerplate?
- Can an operator understand the source materially faster without losing key value?

Use targeted human gold/insight checklists as the primary semantic benchmark where available.

### 3. Auxiliary evaluation

Use DeepEval only where its metric/language/Trial-1 CLI transport can be configured truthfully. It is auxiliary, not final authority.

Use mDeBERTa/HHEM scores as advisory/evaluation data, not hard semantic truth.

### 4. Product baselines

Where practical under Trial-1 transport constraints, compare operator usefulness against Fabric and/or Open Notebook/other transcript knowledge baselines. These are product comparators, not provenance authorities.

## Stage-selection decisions

Make decisions locally, not by redesigning the pipeline:

- S2: faster-whisper config vs Parakeet;
- S3: WhisperX conditional or bypass;
- S6: GLiNER2 retained or bypass;
- S7: LangExtract+CLI vs direct CLI;
- S8: native schema vs Instructor if trigger fired;
- S10: mDeBERTa/HHEM retained as warnings or evaluator-only;
- S11: direct CLI vs DocETL if DocETL test was practical.

A challenger wins only for material measured value. If quality is effectively tied, prefer the simpler/reliable route.

## Full-source expansion rule

Do **not** immediately rerun all four sources after every implementation edit.

Use this progression:

1. one real Map packet product check;
2. one complete short/representative source through S0–S13;
3. inspect the finished knowledge product;
4. only after that route is good, run the four-source regression;
5. then run genuinely fresh English + German audio-to-knowledge demonstrations;
6. run real resume/idempotency behavior against that same selected real semantic route.

This minimizes quota waste and catches wrong-target behavior early.

## Final output contract

Produce/update only after actual product runs exist:

```text
artifacts/transcript_pipeline_v2/SELECTION.yaml
artifacts/transcript_pipeline_v2/FINAL-REPORT.yaml
SourceTranscriptionAnalysisPipeline_Research/v2-reuse-bakeoff/06-FINAL-HANDOVER.md
```

These summarize reality; they are not the primary product.

The handover must state:

- selected component at each stage;
- exact real semantic CLI transport;
- real production entrypoint;
- benchmark/fresh E2E results;
- major limitations/blocked challengers;
- location of the actual final knowledge artifacts.

# 16. End-to-end success condition

The implementation is successful when:

```text
real source/media
 -> real local acquisition
 -> real ASR where required
 -> TTK custody/windows
 -> real allowed subscription-CLI semantic Map
 -> TTK validation
 -> real allowed subscription-CLI Reduce
 -> selective verification where required
 -> TTK compile
 -> useful source-specific knowledge artifact
```

works through one production entrypoint, and stage-local challengers have been either promoted, retained conditionally, rejected, or truthfully blocked based on their own bounded tests.

The next stage always consumes the **declared output of the previous stage**, not a reconstructed narrative from AI memory.
