# 1. Why this file exists

The repository already contains a strong **V2 option architecture** in `01-ARCHITECTURE-ANALYSIS.md`, a V2 implementation task graph, and a V2.1 Trial-1 transport override. What it did **not** contain was one clean V2.1 document that answers the implementation question:

> **Given the V2 research, V2.1 transport lock, current TTK contracts, and the failures of the previous execution attempts, what complete pipeline do we actually recommend building from beginning to end?**

That missing bridge created an authority hazard: the older V1 files were recommendation-shaped and concrete, while V2/V2.1 was spread across architecture, component, benchmark, transport, evaluator, and corrective documents. An execution AI could therefore accidentally combine a V1 recommendation with a V2.1 implementation plan.

This file closes that gap.

It does **not** claim that the invalid V2.1 benchmark runs proved component winners. They did not. This is the **recommended reference production architecture** derived from the V2 research and locked V2.1 constraints. Where V2 correctly requires a measured choice, the stage keeps a clearly named challenger and a narrow promotion rule instead of pretending a winner was already proven.

# 3. Product target

The product is a **trustworthy, high-value, source-grounded knowledge artifact from real audio/video**, not a transcript, validator report, benchmark score, or collection of receipts.

The production route must:

- work on long English and German sources;
- preserve immutable source/transcript evidence;
- use deterministic code for deterministic custody/state/validation work;
- use proven specialized software for narrow solved problems;
- use a real strong subscription CLI AI only for genuinely semantic work;
- preserve important facts, mechanisms, arguments, caveats, contradictions, and uncertainty;
- produce useful Macro/Meso/Micro knowledge with traceable Micro provenance;
- selectively verify only important/checkworthy factual claims;
- resume from file/hash state without repeating valid expensive semantic work;
- remain invokable by APEX/OpenClaw through one thin local runner.

# 5. The actual recommended component composition

This section distinguishes the **recommended hot path**, **conditional stages**, and **challengers/evaluators**. A researched tool is not erased merely because it is not on every production run.

| Stage | Recommended role | Component / route | Status |
|---|---|---|---|
| S0 Trigger | orchestration | APEX/OpenClaw -> thin Python/PowerShell runner | **Core** |
| S1 Acquisition | media acquisition | existing P1 + `yt-dlp` + `ffmpeg` | **Core** |
| S2 ASR | local transcription | calibrated `faster-whisper` | **Recommended reference** |
| S2 ASR challenger | quality/runtime comparison | NVIDIA Parakeet TDT 0.6B v3 | **Must benchmark before ASR freeze** |
| S3 Alignment/speakers | word alignment / diarization | WhisperX (+ pyannote when needed) | **Conditional** |
| S4 Custody | source evidence/state | TTK | **Locked core** |
| S5 Windows | bounded transport packets | TTK | **Locked core** |
| S6 Pre-extraction | cheap entities/relations hints | GLiNER2 | **Optional challenger; never semantic authority** |
| S6 secondary | multilingual schema extraction | NuExtract | **Only if GLiNER2 role fails** |
| S7 Map | grounded semantic extraction | **LangExtract + real allowed CLI provider adapter** | **Recommended grounded route** |
| S7 Map control | semantic reference | direct Claude/Codex CLI | **Required control / fallback** |
| S8 Structured output | shape/retry | native CLI schema + TTK validation | **Recommended** |
| S8 conditional | provider-neutral schema/retry | Instructor/Pydantic | **Only if native seam proves brittle** |
| S9 Map validation | deterministic provenance/invariants | TTK validator | **Locked core** |
| S10 Support advisory | multilingual entailment warning | mDeBERTa NLI | **Recommended advisory if benchmark earns useful signal** |
| S10 English comparator | factual consistency | Vectara HHEM | **Optional English-only advisory** |
| S11 Reduce | global semantic synthesis | direct strong subscription CLI over validated TTK ledger | **Recommended reference** |
| S11 challenger | Map/Reduce orchestration | DocETL fixed pipeline, optimizer off first | **Must receive bounded comparison, not default** |
| S12 Verification | route + evidence judgment | TTK queue + allowed CLI WebSearch/WebFetch/search capability | **Core + semantic worker** |
| S13 Compile | canonical knowledge output | TTK compiler | **Locked core** |
| S14 Evaluation | exact/human/semantic/product comparison | TTK gates + human gold + DeepEval where compatible + Fabric/Open Notebook baselines | **Off-path evaluation** |

### Why LangExtract is recommended for the primary grounded Map implementation

The V2 research identified source-grounded extraction as one of the strongest opportunities to replace fragile custom plumbing. LangExtract is purpose-built for structured extraction with source locations and has a supported provider-plugin mechanism. That means it can sit **inside the Map stage**, while TTK remains canonical custody and the strong subscription CLI remains semantic authority.

The implementation must still keep a direct-CLI Map control. If the CLI-provider adapter is impractical or materially worse, LangExtract is rejected/blocked and the direct route remains production-capable. Do **not** create a homemade imitation of LangExtract.

### Why GLiNER2 is not automatically in the hot path

GLiNER2 is valuable only if its local hints materially reduce strong-AI work or improve structured recall without biasing semantic interpretation. It may extract entities/relations/classification hints, but it may never decide the thesis, semantic chapter boundaries, nuanced support status, or final claims.

### Why DocETL is a challenger rather than the default

DocETL could eliminate meaningful custom semantic orchestration. But TTK already owns transcript-specific custody/state. The first comparison therefore uses the **same validated evidence** and a fixed DocETL pipeline with optimizer off. Promote it only if it improves quality, resilience, or maintenance enough to justify the extra framework/provider seam.

# 6. Trial-1 strong-AI transport

Trial 1 is **subscription CLI only**.

Allowed semantic workers:

1. Claude Code CLI;
2. Codex CLI authenticated through the ChatGPT plan;
3. Antigravity CLI **only after a real headless subprocess smoke passes**.

Deferred/forbidden during Trial 1:

- Gemini CLI;
- browser AI;
- API-key / pay-as-you-go model APIs;
- hosted model APIs;
- the current coding agent or an internal subagent pretending to be one of the allowed CLIs.

A framework such as LangExtract, DocETL, or DeepEval may use strong AI in Trial 1 **only through a bounded adapter that launches an allowed CLI**. If that route is impractical, mark that framework experiment `BLOCKED_FOR_TRIAL1`; do not silently substitute an API or synthetic implementation.

For the first working semantic route, prefer **Claude Code CLI** when its real subprocess route is installed/authenticated and working. Codex is the fallback/challenger. Antigravity is not equivalent to an Antigravity-hosted coding agent; only the actual `agy` CLI process qualifies.

# 7. Canonical stage-to-stage contracts

Each stage must consume only the previous stage's declared output plus stable configuration/authority. This is the chain that prevents accidental cross-stage invention.

| Stage | Input | Main transformation | Output handed forward |
|---|---|---|---|
| S0 Trigger | URL/local source/watchlist event + operator mode | create run identity and bounded request | `run-request.json` |
| S1 Acquisition | `run-request.json` | acquire/media-normalize + metadata/hash | local audio/media + `source-metadata.json` |
| S2 ASR | audio + metadata | speech recognition + timing/telemetry | `transcript.json` + `.srt` + ASR metadata |
| S3 Align/diarize | audio + ASR transcript | forced alignment/speaker labels if needed | alignment/speaker sidecar or enriched transcript |
| S4 Custody | selected transcript representation | TTK init/canonicalization | source SHA + canonical segments/state |
| S5 Windows | canonical segments/state | bounded core/context windowing | TTK Map packet files |
| S6 Pre-extract | one Map packet | optional local hints only | per-window hint sidecar |
| S7 Map | Map packet + optional hints | grounded semantic interpretation | raw TTK Map result |
| S8 Structured output | semantic request/result schema | schema enforcement + bounded retry | schema-valid candidate result |
| S9 Map validation | packet + Map result | deterministic provenance/freshness/coverage checks | validated Map set + Reduce packet/ledger |
| S10 Support advisory | factual claim/evidence pairs | local independent warning signals | advisory sidecar, never silent override |
| S11 Reduce | validated compact evidence ledger + advisory warnings | global semantic synthesis | TTK Reduce result |
| S12 Verify | TTK verification queue | targeted external research/judgment | verification results / `UNVERIFIED` |
| S13 Compile | validated Reduce + verification state | deterministic knowledge compilation | final wiki + canonical machine artifacts |
| S14 Evaluate | final product + source/gold/baselines | product and architecture evaluation | selection + final report + production handoff |

No stage should reread arbitrary earlier repository/history material merely because it exists.

# 8. Context management is part of the architecture

The next execution must not preload the entire research corpus into one AI context.

## 8.1 Stable context

At the beginning of the overall run, load only:

1. `06-TRIAL1-TRANSPORT-LOCK.yaml`;
2. this file;
3. `09-V2.1-TARGET-FIRST-EXECUTION-BRIEF.md`.

Use `07-DECIDED-FRAMEWORK-AND-TEST-EVALUATION-HANDOVER.yaml` only to resolve a real ambiguity about what is locked/open.

## 8.2 Stage-local context

For each stage, the executing AI loads:

- the matching chapter in `11-V2.1-STAGE-BY-STAGE-IMPLEMENTATION-PLAN.md`;
- the **previous stage handoff** and exact input artifacts;
- only the relevant component-registry entry / owning code files named by that chapter.

Do **not** reread the entire V2 architecture, component registry, benchmark spec, all historical failures, and every prior run at every stage.

## 8.3 Lightweight stage handoff

At each completed stage, preserve one compact handoff containing only:

- stage ID and status;
- input artifact paths + hashes;
- component/version/config actually used;
- output artifact paths + hashes;
- important measured result or limitation;
- next stage ID.

This is a context boundary, not a new validation framework. The next stage should be able to start from the handoff and its declared inputs without reconstructing the previous stage from chat history.

# 9. Product-quality rules that survive every stage

1. **No pseudo-semantics.** Regex, keyword lists, fixed templates, sentence splitting, or the coding agent itself may not replace real semantic interpretation.
2. **No fake freshness.** A fresh audio/ASR run begins from real newly acquired/materialized media and an actual ASR invocation.
3. **No cross-source contamination.** Every Map/Reduce/wiki product must remain bound to one source/run identity.
4. **Quote/span existence is provenance, not semantic entailment.** Source support remains a semantic judgment.
5. **Processing windows are not Meso chapters.** Meso structure is decided globally during Reduce.
6. **Facts and testable estimates need exact source evidence.** Non-factual semantic objects need provenance but not forced quote quotas.
7. **External truth is separate from source support.** A source can clearly state something that external evidence contradicts.
8. **Resume from state.** Unchanged valid semantic work is reused; changed upstream data invalidates only dependent work.
9. **Actual artifact quality outranks PASS labels.** A schema-valid but wrong-source or generic wiki is a failed product.

# 10. What must be tested before the architecture is frozen

The recommended reference architecture is concrete, but four stage decisions still deserve real bounded comparisons because the V2 research found plausible material value:

1. **ASR:** calibrated faster-whisper vs Parakeet on the same hard EN/DE slices.
2. **Map:** direct CLI control vs LangExtract+CLI; GLiNER2-assisted lane only to test whether hints earn their cost.
3. **Support advisory:** mDeBERTa (and HHEM on English) against human-reviewed claim/evidence pairs.
4. **Reduce:** direct CLI vs fixed DocETL if a Trial-1-compliant CLI adapter is practical.

These are **stage-local comparisons**, not permission to rerun the entire pipeline for every candidate.

A challenger is promoted only for material gain in at least one of:

- accuracy / insight recall;
- grounding / evidence quality;
- semantic reliability;
- token/quota efficiency;
- runtime / memory feasibility;
- operator usefulness;
- meaningful custom-code elimination;

without disproportionate complexity or a hard correctness/provenance failure.

# 11. Recommended final production shape if the bounded challengers do not overturn it

```text
APEX/OpenClaw
  -> thin deterministic runner
  -> existing yt-dlp/ffmpeg acquisition
  -> calibrated faster-whisper
  -> WhisperX only for sources that need speaker/alignment enrichment
  -> TTK canonical custody + windows
  -> LangExtract grounded Map using real Claude Code CLI provider adapter
       (direct Claude/Codex CLI remains the control/fallback)
  -> native CLI structured output + TTK deterministic Map validation
  -> mDeBERTa advisory warnings on factual support pairs
       (+ HHEM only where useful on English)
  -> direct real subscription-CLI Reduce over validated TTK evidence ledger
  -> TTK selective factual verification queue
  -> allowed subscription-CLI research for queued claims
  -> TTK compiler
  -> final machine-readable knowledge + operator wiki
  -> off-path human/deterministic/DeepEval/baseline evaluation
  -> APEX/OpenClaw production handoff
```

If a stage-local challenger materially wins, replace **that stage only** while preserving the input/output contract. Do not redesign unrelated stages.
