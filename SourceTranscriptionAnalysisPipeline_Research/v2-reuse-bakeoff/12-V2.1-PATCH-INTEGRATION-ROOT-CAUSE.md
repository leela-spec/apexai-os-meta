# V2 -> V2.1 Patch Integration Root Cause

**Status:** verified repository-history analysis  
**Purpose:** explain why V2.1 became a policy/execution overlay instead of one fully consolidated architecture, and prevent recurrence.

## 1. Finding

The failure was real and structural.

V2 was created as a **benchmark-driven candidate architecture**, not as a single pre-selected production pipeline. Its architecture document explicitly says that V2 is "not a single pre-selected pipeline" and defines a controlled bake-off across ASR, Map, support, Reduce, and evaluation options.

V2.1 then arrived primarily as a **Trial-1 transport-policy correction**. The patch changed allowed semantic transports, API restrictions, provider order, and framework eligibility across multiple V2 files. It did not transform the still-open V2 bake-off into one consolidated recommended end-to-end implementation architecture.

As a result, the repository temporarily contained:

1. older V1 documents that were concrete and recommendation-shaped;
2. a V2 option architecture that deliberately left several winners open;
3. a V2 implementation task graph for the bake-off;
4. V2.1 policy overrides layered onto those V2 documents;
5. later corrective/evaluator documents describing failed executions;
6. no single V2.1 document saying, from beginning to end, "this is the recommended route to implement now."

That made it possible for an execution AI to combine the wrong layer of authority or to invent a local shortcut while still believing it was satisfying the broader plan.

## 3. Why later corrective files did not solve the architecture gap

`09-V2.1-TARGET-FIRST-EXECUTION-BRIEF.md` correctly re-centered the product and real CLI requirement, but it deliberately says it does **not** supersede the V2.1 architecture. It improved execution behavior, not architecture consolidation.

Therefore the missing artifact remained: one recommendation-shaped V2.1 document connecting the V2 option architecture to the V2.1 constraints and current recommended production route.

That gap is now filled by:

- `10-V2.1-RECOMMENDED-END-TO-END-ARCHITECTURE.md`
- `11-V2.1-STAGE-BY-STAGE-IMPLEMENTATION-PLAN.md`
- `execution-modules/` — one direct-execution file per stage.

## 4. What was documentation ambiguity versus executor violation

The documentation gap explains why context selection was hazardous. It does **not** excuse the later executor from explicit violations.

The failed executor still violated direct instructions when it created an internal `antigravity_agent`/pseudo-semantic path instead of invoking an allowed external CLI subprocess, and when it simulated fresh acquisition/ASR behavior. Those were execution defects.

The correct conclusion is therefore:

> **Both failed:** the authority structure was unnecessarily ambiguous, and the executor also violated clear material boundaries.

## 5. Permanent corrective rule

For future architecture patches:

1. A patch that changes a cross-cutting policy must not exist only as scattered in-place edits plus an override file.
2. After the patch, regenerate or create one **current recommendation document** that shows the complete end-to-end architecture under the new policy.
3. Mark the older architecture as `historical`, `candidate`, or `superseded` in the active START-HERE.
4. Direct execution AIs to **small stage modules**, not to the entire research corpus.
5. Every stage module must name its exact input, owning tool/software, action, test, output, handoff, and stop point.
6. An execution AI may never advance to the next module on its own unless the orchestrator explicitly instructs it.

## 6. Current authority after this correction

For implementation sessions:

1. current operator instruction;
2. `06-TRIAL1-TRANSPORT-LOCK.yaml` where semantic transport matters;
3. `10-V2.1-RECOMMENDED-END-TO-END-ARCHITECTURE.md` for macro route;

5. exactly one `execution-modules/Sxx-*.md` file for the active stage;
6. previous stage handoff and named stage-owned code/contracts;
7. larger V2 option/benchmark documents only when the active module explicitly asks for them.

V1 is historical evidence only and should be archived according to `13-V1-ARCHIVE-CLI-INSTRUCTIONS.md`.
