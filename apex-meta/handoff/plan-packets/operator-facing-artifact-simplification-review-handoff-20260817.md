# Handover — Operator-Facing Orchestration Artifact Review and Simplification

## Objective

Review the current Apex weekly/daily orchestration artifacts with the operator and determine whether the present artifact architecture is unnecessarily machine-oriented, over-specified, or over-engineered. The target is an **efficient, resilient, simple, operator-comprehensible orchestration flow that stays on target and does not drift**.

Do not assume the current schemas, files, variables, gates, or per-flow artifacts are necessary merely because they exist. Treat simplification as a first-class design goal. Preserve only structure that demonstrably protects correctness, authority boundaries, evidence lineage, deterministic computation, or reliable automation.

## Operator concern to investigate

The operator reviewed the newly created ProjectStatus, weekly-plan, next-day, flow-packet, and prompt-pack artifacts and found them extremely difficult to understand. They appear primarily machine-readable: large YAML structures, many variables, statuses, enums, metadata fields, references, data series, and nested contracts.

The operator recalls that the system had previously been designed to include **human-facing files/views distinct from machine-facing state/contracts**. They want this verified against repository truth rather than memory.

The operator suspects that the current design may have drifted into over-engineering: AI agents now need to understand many internal fields that may not create proportional real-world value, while the operator cannot efficiently inspect or approve the resulting plans.

## Required questions to answer with the operator

1. **What are all the files created in the current W34 flow, and what is each actually for?**
   - Which are operator-facing?
   - Which are machine-facing?
   - Which are contracts/templates versus run artifacts?
   - Which are durable state versus disposable planning/intermediate files?
   - Which files are authoritative, candidate-only, derived, or redundant?

2. **Was a human-facing presentation layer previously designed?**
   - Search the repository and history/commits where useful.
   - Identify exact files/commits/decisions that support or contradict this recollection.
   - Determine whether it was implemented, partially implemented, superseded, or lost through later architecture changes.
   - Do not infer this from naming alone.

3. **Why do the current artifacts contain so many variables and schema fields?**
   - For each major field family, state the concrete failure it prevents or automation capability it enables.
   - Distinguish genuine invariants from speculative future-proofing.
   - Identify fields that are duplicated, derived, never consumed, only decorative, or maintained because another schema requires them.
   - Identify where an AI is being asked to maintain data that could instead be deterministic, implicit, derived on read, or deleted entirely.

4. **How were the current files actually created?**
   - Identify which artifacts were generated by deterministic scripts, which were authored/generated by an AI from skill contracts, and which were manually/operator supplied.
   - Do not use vague language such as “the system created it.”
   - For the W34 run, trace provenance file by file from commits, agent/skill contracts, scripts, and source inputs.
   - Clarify whether the result is deterministic, AI-generated under deterministic schema constraints, or genuinely nondeterministic.

5. **Is the current multi-file architecture necessary?**
   Evaluate at minimum:
   - ProjectStatus overview
   - weekly_plan_packet
   - next_day_plan
   - F1-F4 flow_packet files
   - F1-F4 flow_prompt_pack files
   - prompt packet body files when materialized
   - raw-flow-dump / normalized evidence files
   - flow_recap_packet files
   - status_merge_packet
   - Session handoff/state artifacts
   - Sync reports

   For each, decide one of:
   - keep as-is
   - simplify
   - derive automatically
   - merge with another artifact
   - hide from operator but retain internally
   - make ephemeral
   - delete

6. **Where should the human/machine boundary be?**
   Design a minimal target model in which:
   - the operator sees only information needed to understand, decide, approve, execute, or correct;
   - machine-only metadata is hidden or stored separately;
   - agents do not repeatedly reproduce large schema boilerplate;
   - deterministic values are computed, not authored by LLMs;
   - no field exists without a named consumer and concrete value;
   - operator gates are concise and decision-oriented;
   - evidence lineage and mutation safety remain reliable.

7. **Can one human-facing artifact drive the daily workflow?**
   Explicitly test whether a compact daily operator file/view could contain, for example:
   - Today’s intent
   - 1-4 flows
   - concrete task/outcome per flow
   - why this is next
   - expected output / done condition
   - blockers/questions
   - execution prompt/link/reference only when needed
   - what evidence to return
   - one approval surface

   Machine metadata could then be generated/derived behind it rather than exposed to the operator. Do not adopt this proposal automatically; evaluate it against actual downstream requirements.

## Current repo-level concern already observed

The active architecture mixes several roles inside Markdown files:

- orchestration handoff envelope
- schema-shaped planning data
- operator review state
- source/provenance references
- validation flags
- planning content
- human summary

This may be justified in some places, but it creates operator cognitive load and repeated token/LLM burden. Determine whether these concerns can be separated without weakening reliability.

## Evaluation principles

Use these as hard design criteria:

### 1. Operator comprehension
A normal operator review should not require understanding internal schema fields, lifecycle enums, authority metadata, validation plumbing, or cross-package contracts unless a problem specifically needs them.

### 2. Named consumer rule
Every retained field must have a named consumer. If no current code, skill, agent, validator, or operator decision actually consumes it, it is a deletion candidate.

### 3. Deterministic-before-LLM
Anything that can be derived deterministically from paths, task state, timestamps, fixed mappings, or prior artifacts should not require an LLM to author/restate it repeatedly.

### 4. Single source of truth
Do not duplicate the same status, project mapping, role, source path, or validation state across multiple files unless the duplication prevents a specific demonstrated failure.

### 5. Progressive disclosure
Machine plumbing may exist, but the operator should see a compact decision view first. Internal detail should be inspectable only when useful.

### 6. Evidence and authority safety
Simplification must not erase:
- candidate versus confirmed distinction
- source/evidence lineage where consequential
- operator confirmation for consequential mutations
- dependency/blocker integrity
- protection against false execution claims

### 7. Automation compatibility
The target architecture must remain compatible with the intended automated pipeline. Avoid “simplification” that merely shifts manual bookkeeping back onto the operator.

### 8. No speculative architecture
Do not introduce new layers, databases, registries, schemas, adapters, or services unless a concrete current requirement cannot be met more simply.

## Required working method with the operator

Do **not** immediately redesign or modify the skills.

First conduct an interactive review in this order:

1. Explain the current artifact chain in plain language.
2. Walk through each current W34 file and state its real value and consumer.
3. Explain provenance: deterministic script vs AI-generated vs operator-authored.
4. Identify obvious redundancy / machine-only boilerplate.
5. Recover any earlier human-facing design from repository history if it exists.
6. Present a minimal current-state diagram.
7. Present 2-3 simplification options ranging from conservative to aggressive.
8. Discuss tradeoffs with the operator.
9. Only after operator agreement, produce a concrete skill/agent change proposal.
10. Do not mutate production skills, schemas, or W34 artifacts until explicitly approved.

## Success criteria

The review is successful only if the operator can answer all of these without reading machine schemas:

- What files exist and why?
- Which ones do I actually need to read?
- Which ones are created deterministically and which ones rely on AI judgment?
- What information is genuinely protecting the system from failure?
- What can be deleted or hidden?
- What is the minimal human-facing weekly/daily workflow?
- How will automation continue without adding manual work?
- How will the design prevent future architectural drift and over-engineering?

## Stop condition

Stop after the analysis, options, and operator decisions are clear. Do not implement the redesign until the operator explicitly approves a specific target architecture.
