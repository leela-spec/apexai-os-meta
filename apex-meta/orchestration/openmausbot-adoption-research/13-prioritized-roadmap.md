# Priority sequence and next work

## Priority method

Prioritize work that can invalidate the integration before work that merely makes it more convenient.
This ordering derives from the existing invariants and observed product behavior.
It is a proposed roadmap, not a newly registered APEX epic or an execution authorization.

## P2 — Expand to selected domains

1. Choose the next story based on actual operator demand.
2. Reconcile the corresponding WF plan with current infrastructure.
3. Read the target service's official documentation and existing canonical skill.
4. Verify service identity and least required operations.
5. Rehearse in an authorized test scope.
6. Capture domain acceptance receipts.
7. Enable recurrence only after duplicate/recovery behavior is proven.
8. Package the accepted configuration if portability provides real value.

Investment, financial, legal, and physical-safety workflows require their existing stronger boundaries.
Do not migrate all ten workflow plans merely to populate a team.

## Research gaps worth funding next

### Highest information value

- Exact native project-agent and skill behavior in installed OpenMausBot.
- Effective reviewer context and tools.
- Authority sidecar/dependency closure in the actual mutation path.
- Current Windows-versus-WSL repository and service map.
- Whether product-native peer history can meet fresh-review requirements.

### Defer until needed

- A complete all-provider comparison.
- A new agent framework or generic lifecycle engine.
- Organization-wide template distribution.
- Public remote hosting.
- Automatic bidirectional project synchronization.
- Full automation of financial workflows.
- Broad skill duplication across every bot.

These are deferred proposals, not claims that the product cannot support them.
