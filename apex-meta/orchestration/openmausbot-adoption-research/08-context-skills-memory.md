# Context, skills, memory, and knowledge

## Keep one authority for each kind of knowledge

Use repository indexes for accepted doctrine and procedure discovery.
Use run packets for changing execution state.
Use product memory only for limited convenience information that cannot authorize or validate a mutation.

This is an APEX-specific proposal grounded in [A01/A21](14-source-register.md#apex-source-register).
The product supports memory; it does not prescribe this authority allocation.

## Context layers

| Layer | Contents | Load rule | Owner |
|---|---|---|---|
| Standing profile | Purpose, activation boundary, canonical pointers | Every relevant conversation | Accepted role configuration |
| Current task packet | Objective, sources, tools, output, stop condition | Each bounded assignment | Meta Ops |
| Procedure | Existing Skill and required references | Task trigger | Canonical skill owner |
| Evidence | Exact source slices and full accessible references | Just in time | Source owner |
| Review context | Frozen subject and one lens | Fresh review invocation | Review packet builder |
| Candidate learning | Proposed improvement and supporting run evidence | Separate review | No self-promotion |

Do not paste the whole research project into a bot's system prompt.
The [index](index.md) routes the next agent to the relevant dimension.

## Native project skills versus imported product skills

Existing APEX skills depend on supporting references and templates.
Some also carry runtime semantics such as context: fork.
A file being visible or imported does not prove those semantics execute.

The pinned OpenMausBot skill source describes prompt indexing and native discovery links.
Its import paths and team package format are not necessarily identical.
The team-sharing documentation includes richer packages than the narrow import comment.

Proposed first approach: use canonical project skills through the verified native engine route.
Preserve their original relative references.
Do not rewrite all procedures into OpenMausBot memory or duplicate them across profiles.
Sources: [S08](14-source-register.md#s08), [S09](14-source-register.md#s09), [S23–S24](14-source-register.md#s23).

## Required skill portability test

For each required skill, record:

1. Discovery path visible to the actual engine.
2. Exact SKILL.md hash.
3. Required supporting files and whether they resolve.
4. Invocation mechanism actually used.
5. Whether context isolation occurred where required.
6. Available tools during execution.
7. Output envelope and target location.
8. Behavior on a missing reference.
9. Whether imported content remains disabled until reviewed.
10. Any difference between native, imported, and packaged execution.

Initial set: apex-plan, apex-sync, apex-session, source-authority-and-verdict-packet.
Add lane skills only when the selected pilot calls them.
Weekly migration separately tests its stage skills and review wiring.

## Provider configuration matters

Official OpenMausBot documentation says Claude bots normally use project settings and the app's selected MCP configuration.
User-level Claude skills, hooks, personal CLAUDE.md, and MCP inheritance are not all automatically included.
The optional user-MCP switch does not restore every user-level behavior.

Codex personal configuration can still supply MCP servers outside the product's per-bot server selection.
Therefore a visually empty app MCP list is not proof of an empty effective tool list.
Capture actual engine/tool behavior for the chosen account.
Source: [S08](14-source-register.md#s08).

## Memory policy proposal

### Controller

Keep short pointers to accepted APEX entry points and operator presentation preferences.
Reload run state from files at each resume.
Do not store “the operator approved X” as an authority-bearing memory.
Link the immutable decision record instead.

### Production specialists

Optional memory may contain stable terminology pointers and reusable non-authoritative context.
A new assignment still receives a complete packet.
Memory must not widen its target surface or grant access.

### Detective

Prefer fresh native read-only reviewer contexts for the first pilot.
If persistent product reviewer bots are considered, demonstrate absence of forbidden memory, recall, and peer history.
Separate names or empty current transcripts are insufficient proof.
Include the workspace-wide About me profile in that inspection.
Official configuration docs say its content enters subsequent private and group turns across providers.
Source: [S17](14-source-register.md#s17).

### Learning

A useful observation becomes candidate learning with evidence and a named owner.
It becomes accepted doctrine only after the existing review and operator process.
Product skill-learning convenience does not replace this transition.

## OpenProject and knowledge services

Reuse the existing service skill after reading its own canonical entry point.
The later OpenProject handover explicitly requires review of prior research before implementing its integration.
This project records that dependency; it does not create another OpenProject client or new taxonomy.

This research folder is a research bundle, not an initialized controlled knowledge base.
No ingestion manifest or canonical KB state was fabricated.

## Export discipline

A team package may carry instructions and starter notes.
Inspect exactly what will be shared.
Exclude private context and pending approvals from reusable packages.
Keep model/account bindings and secrets in local deployment configuration.
Treat package import as candidate configuration awaiting the accepted pilot checks.
