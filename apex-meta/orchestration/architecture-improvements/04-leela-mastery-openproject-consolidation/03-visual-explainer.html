OpenProject setup · plain-language diagnosis

Why the AI agents can't reach OpenProject yet

Two separate, fixable problems are in the way. This page shows — with pictures — where every piece lives, how they're meant to talk to each other, where the wire is broken, and the choices for fixing it. No prior technical knowledge needed.

The 15-second version

Your computer is really two computers: Windows, and a smaller private computer inside it called WSL. OpenProject lives in the WSL one and only opens its door on WSL's private hallway. The AI agents live in the Windows one and knock on Windows's hallway — so nobody answers. Problem 2: even once they get in, the "Leela" project hasn't switched on the kinds of work-item it needs (Epic, Feature, Story). Nothing is broken or lost — both are setup steps, and the first decision is which side the skill should run on.

03 · WHAT BREAKS

What actually happens right now

The skill sends its request to the address it was told to use — 127.0.0.1:8083. The catch: 127.0.0.1 means "this same house". From the Windows house, that points at the Windows hallway. But OpenProject's door is in the WSL hallway. Same address written down — two different hallways. So the knock lands on an empty wall.

Why this was missed earlier: the setup was written assuming 127.0.0.1:8083 works from both houses — a note in the config file even says so. Nobody tested it from the Windows side until now. That was the blind spot.

04 · WHY

Why: the "private door" vs the "all-doors" setting

When OpenProject was started, its door was set to open only on the WSL house's private address (127.0.0.1). There's another setting: open on all of the WSL computer's network addresses (0.0.0.0) — a binding that WSL can forward to Windows's localhost. Whether that forwarding works here is something we test, not assume. Same OpenProject — just which addresses its door listens on.

05 · THE SECOND, SEPARATE PROBLEM

The Leela project hasn't switched on the right work-item types

This one has nothing to do with the connection. Work-item types are set by each instance's admin, and each project then chooses which of them it uses. As checked on 2026-09-27, this instance defines seven types, and the Leela project has only three switched on. The plan needs Epic, Feature and User story too — so creating an "Epic" there is correctly refused until they're enabled for that project (an admin toggle, ~1 minute).

06 · THE REAL FIRST QUESTION

First decide: which side should the skill run on?

The three fixes below aren't really ranked best-to-worst — they follow from one architecture choice: should the skill run inside WSL (next to OpenProject), or stay a Windows program? For a privacy-first, self-hosted setup, running it inside WSL (option C) is a strong, clean choice — and it's also the quickest way to finish testing the real skill, because inside WSL the connection already works.

Recommended for this setup

C · Skill runs inside WSL

Install Node inside WSL; every agent calls it through one identical Windows launcher (wsl … node opCall.js …).

  • ✓ Same skill code, guards & config for all 5 agents
  • ✓ OpenProject stays private (loopback) — nothing newly exposed
  • ✓ No networking change; unblocks the real skill test today
  • ✗ A second Node runtime + a uniform launcher to maintain
Viable, needs hardening

A · Open all WSL addresses

Publish OpenProject on 0.0.0.0 so Windows can reach it; add a firewall guard so only your PC can.

  • ✓ Skill runs on Windows as originally designed
  • ✗ Widens exposure — needs a firewall rule + a 3-way test
  • ✗ Needs a one-time Docker permission
Bigger switch

B · "Mirrored" networking

Flip a Windows-wide setting so both houses share one hallway.

  • ✓ Keeps the private-address setting
  • ✗ Affects every WSL app (incl. your other stack)
  • ✗ Known quirks; needs a full WSL restart

09 · GLOSSARY

Plain-language glossary

Windows host
Your actual PC and its main operating system — where you work and where the AI agents run.
WSL
"Windows Subsystem for Linux" — a small, complete Linux computer running inside Windows. It has its own separate network.
Container / Docker
Docker packages an app (like OpenProject) into a self-contained box called a container. All the containers here run inside the WSL computer.
OpenProject
The project-management app itself — the thing that will hold all your epics, tasks and dependencies.
Port :8083
A numbered "door" on a computer. OpenProject answers on door 8083.
127.0.0.1 / localhost
Means "this same computer." The problem: Windows and WSL each have their own "this computer," so the same address points to different places.
0.0.0.0
Means "listen on all of this computer's network addresses" — the binding WSL can forward to Windows's localhost.
The agents
Your AI accounts (Claude Code, Codex ×2, Antigravity) — all running as Windows programs.
The skill package
A small program (opCall.js) the agents run to talk to OpenProject safely — with a preview-and-confirm step before any change.
doctor / self-check
A read-only command the skill should have that verifies everything (reachability, login, right instance, project, allowed types, write-gate) before any real work.
API
OpenProject's official "service window" that other programs are allowed to talk to.
Work-item types
The shapes of work: Epic, Feature, User story, Task, Milestone, etc. Each instance's admin defines them; each project switches on the ones it uses.
