| **D-15** | **Private-stack DB migration onto the shared cluster uses per-dump handling, not a single uniform command:** `priv_firefly` and `priv_openproject` restore cleanly with `pg_restore --role=priv_*_app` (SET ROLE) same as community; `priv_paperless` needs the non-trusted `vector` (pgvector) extension **pre-created as superuser** first (its dump's own `CREATE EXTENSION IF NOT EXISTS vector` then no-ops under `--role`); `priv_openproject`'s dump — produced by `leela-op178-openproject`'s **embedded PostgreSQL 17** — needs a **pg17-capable `pg_restore` client** (pg16's can't read the archive format), done via a throwaway `postgres:17` container attached to `shared-db-net` for that one restore only (never touched the live `leela-op178-openproject` container itself). | **accepted** | `btree_gist`/`pg_trgm`/`unaccent` are Postgres "trusted" extensions (installable by any DB-owning role since PG13); `vector` is not, so `--role`'s `SET ROLE` mid-restore hits `permission denied ... must be superuser`. Confirmed by inspecting each dump's TOC before restoring (`pg_restore -l \| grep EXTENSION`), not by guessing. `REASSIGN OWNED BY postgres` was tried as a fix-after-the-fact and **fails outright** ("cannot reassign ownership of objects owned by role postgres because they are required by the database system") — pre-staging the extension before the `--role` restore is the working pattern, not reassignment after. Two further **expected, non-fatal** `pg_restore` warnings appeared and were verified harmless before moving on: `COMMENT ON EXTENSION vector` (needs extension *ownership*, not just `--role`'s table ownership — cosmetic metadata only) and `SET transaction_timeout = 0` (a PG17-only session GUC in the pg17-dump preamble that pg16 doesn't recognize — one skipped `SET`, not a data-affecting statement). Row counts + `pg_tables.tableowner` verified correct after each fix. **If this turns out wrong:** re-check `pg_extension`/`pg_tables.tableowner` in `priv_paperless`/`priv_openproject` for anything still owned by `postgres` instead of the app role; the two warnings above are the only ones that should ever appear — any additional warning during a future re-run of this restore needs fresh investigation, not an assumption that it's "probably fine like last time." |
