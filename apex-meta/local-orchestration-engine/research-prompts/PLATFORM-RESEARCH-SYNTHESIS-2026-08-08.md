# Cross-Candidate Synthesis Prompt — OpenClaw / Hermes / Odysseus / FEE / Hybrid

## Mission

Synthesize the three independent candidate research reports for OpenClaw, Hermes and Odysseus together with the existing APEX/FEE architecture evidence. Recommend one or more evidence-supported platform compositions for the bounded local execution layer.

Do **not** assume:

- one platform must win everything;
- highest weighted score automatically wins;
- OpenClaw should win because existing doctrine already exists;
- Hermes is merely a notifier;
- Odysseus is already the executor;
- Custom/FEE must implement every browser/tool feature itself.

The architecture goal is not maximum autonomy. It is **safe operational absorption**: move routine human and Claude Code/Codex work into the cheapest reliable layer while preserving strategy, consequential judgement and difficult coding in the correct higher layers.

## Locked architecture

```text
Layer 4 — subscription/deep-reasoning AI
  strategy, planning, research, synthesis, judgement

Layer 3 — scarce CLI AI
  difficult coding, architecture, hard debugging, consequential verification

Layer 2 — bounded local execution operator
  browser/tool operations, mechanical work, small recovery, evidence, escalation

Layer 1 — deterministic execution
  Python/PowerShell/Git/validators/ledgers/exact transforms
```

The local execution substrate must **not become a third APEX orchestration authority** beside Weekly Orchestrator and Multi-Agent Orchestration.

APEX/FEE is currently the default candidate for deterministic work packets, capability boundaries, state/checkpoints, evidence and escalation.

## Operator-confirmed Round-2 constraints

Treat these as requirements:

1. FEE spine + replaceable execution runtime is preferred over a monolith unless evidence strongly reverses it.
2. OpenClaw may be decomposed into runtime capabilities and higher-level doctrine/process roles.
3. Work packets declare fresh vs persistent browser sessions.
4. Browser control should support layered/provider-specific adapters behind a common contract.
5. Local browser recovery is bounded; auth/CAPTCHA/account/payment/security ambiguity stops/escalates.
6. Local edits are bounded/mechanical by default, not general code repair.
7. Tools should be authorized action IDs + independently validated arguments, not arbitrary shell generated by model text.
8. Jobs may declare multiple roots/repos with distinct read/write permissions.
9. Git authority is capability-based; destructive history operations remain prohibited/escalated.
10. Project and personal automation require separate trust profiles.
11. Local-model research compares multiple capability/resource classes; no size is selected yet.
12. Model selection will use real task fixtures, refusal/recovery/escalation/containment and resource coexistence rather than generic leaderboards alone.
13. Initial model-action concurrency is conservative; large artifacts remain on disk and are referenced by path/hash.
14. Overnight blocked jobs checkpoint while independent safe work may continue.
15. Structured event ledger is mandatory; screenshots are selective supporting evidence.
16. Captured browser/model/source content has zero executable authority.

## Mandatory user-flow comparison

Compare all candidate compositions against the same six flows:

- **UF-A Subscription research executor**
- **UF-B Script failure recovery**
- **UF-C Detective evidence collection**
- **UF-D Database / knowledge hygiene**
- **UF-E Multi-repo / multi-folder execution**
- **UF-F Personal weekly execution**

Do not average away a severe failure in one critical flow.

## Hard gates

A primary composition must satisfy, natively or through a thin explicit broker:

1. authority containment;
2. job-scoped permissions;
3. resumability;
4. evidence capture;
5. safe escalation;
6. practical Windows viability.

Any unmitigated hard-gate failure disqualifies a composition as the primary execution path regardless of aggregate score.

## Compositions to compare

At minimum evaluate:

### Composition 1
```text
APEX/FEE deterministic spine
+ Hermes execution/tool runtime
+ OpenClaw higher-level Detective/KB/Hygiene/process doctrine where useful
```

### Composition 2
```text
APEX/FEE deterministic spine
+ Odysseus runtime/tool workspace
+ OpenClaw higher-level processes where useful
```

### Composition 3
```text
APEX/FEE deterministic spine
+ OpenClaw runtime capabilities
+ OpenClaw higher-level doctrine kept authority-separated
```

### Composition 4
```text
Custom/FEE executor
+ provider-specific browser adapters
+ selected reusable components only from Hermes/Odysseus/OpenClaw
```

### Composition 5
```text
APEX/FEE spine
+ different specialized runtimes per user-flow class
```

### Composition 6
Any other evidence-supported hybrid emerging from the independent reports.

Do not reward complexity for its own sake. A hybrid is justified only when added components deliver material value and interfaces remain understandable, testable and maintainable.

For each composition score 0–100 with confidence 0–100:

| RECOVERY | 10 |
| AUDIT | 9 |
| MULTIROOT | 8 |
| LOCALMODEL | 5 |
| WINDOWS | 4 |
| RESOURCE | 3 |
| MAINT | 2 |

Also score:

- CLI_SAVE — expected reduction in Claude Code/Codex operational use;
- HUMAN_SAVE — expected reduction in operator interventions;
- DRIFT — resistance to becoming a competing orchestration authority;
- INTEGRATION — simplicity/clarity of boundaries between components;
- REVERSIBILITY — ease of swapping runtime/browser/model later.

Keep design estimates separate from measured results.

## Architecture economics

For every serious finalist estimate directionally:

- number of custom components to build;
- browser integration burden;
- Windows installation/maintenance burden;
- local-model compatibility constraints;
- RAM/CPU/GPU overhead before model load;
- browser coexistence risk;
- number of persistent services/processes;
- likely failure surfaces;
- upgrade/churn risk;
- likely Claude Code/Codex escalation burden;
- likely human intervention burden.

Do not fabricate exact resource measurements when none exist. Convert unknowns into bake-off requirements.

## Contradiction handling

The three reports were intentionally researched independently. Preserve disagreements.

For every major contradiction:

1. show Candidate Report A claim;
2. show Candidate Report B or source conflict;
3. identify evidence type/recency/version behind each;
4. determine whether the conflict can be resolved from primary sources;
5. if not, define a local test that resolves it.

Do not silently choose whichever report sounds more confident.

## Required local bake-off plan

Desk research must not directly authorize implementation. For the top surviving compositions, define a minimal isolated bake-off using the same fixture corpus.

Include tests for:

- UF-A authenticated browser prompt/capture;
- fresh and persistent conversation handling;
- browser timeout/missing-button/logout/CAPTCHA stop behavior;
- UF-B safe script recovery;
- unauthorized shell/action rejection;
- UF-C evidence collection without verdict drift;
- UF-D bounded hygiene + semantic ambiguity escalation;
- UF-E multi-root read/write containment and forbidden-root rejection;
- UF-F trust-profile separation;
- prompt-injection text that tries to create commands;
- crash/restart resumability;
- blocked overnight job + continuation of an independent job;
- event-ledger/provenance reconstruction;
- peak RAM/CPU/GPU and browser/development-tool coexistence;
- human interventions and CLI escalations.

Use the **same local model candidate where technically possible** during platform tests so runtime quality is not confused with model quality.

## Decision logic

Return three levels of recommendation:

### A. Recommended architecture hypothesis
The strongest composition to take into bake-off.

### B. Runner-up / reversal option
The composition to use if a named bake-off condition fails.

### C. Components worth reusing regardless of primary runtime
Examples could include OpenClaw doctrine, a Hermes notification/session component, an Odysseus workspace capability, or provider-specific adapters—but only if evidence supports them.
