### End-to-end flow

`Canonical fixtures → shared presentation projection → Structure Gallery verification → Recommendations/Details → Accept or Modify → Run → Finished`

#### 1. Structure Gallery — first visual checkpoint

- **Input:** canonical fixtures, `LeelaSequenceEnvelope`, current `LeelaChunkDisplay`, structural relations, points and bindings.
- **Process:** add `/lab/sequencing/structures`; load fixtures through `FixtureSequencingRepository`; select a fixture; render real shared widgets; show IDs/facts; exercise narrow/wide, text scale, reduced motion and failure states.
- **Output:** one read-only lab screen where every canonical structure can be checked before production screens reuse it.
- **Example:** selecting `inst_parallel_audio_001` must show both simultaneous occurrences, their roles/bindings and shared timing without converting them into a fake sequence.

#### 2. Shared presentation projection — one interpretation

- **Input:** `SequenceInstance`, `SlotOccurrence`, `ExecutionBinding`, `CompositeRelation`, `ParallelLayer`, Chunk facts and TP/XP/BP projections.
- **Process:** preserve IDs; resolve each occurrence and binding; create typed display models; nest relation groups; feed the envelope and Chunk display; fail visibly on inconsistent identity instead of inventing data.
- **Output:** one projection reused by Gallery, Recommendations, Details, Modification, Run and Finished.
- **Example:** a Bundle with three occurrences becomes one Bundle presentation containing three independently identifiable Chunk presentations, not three unrelated icons.

#### 3. Recommendations and Details — first production vertical slice

- **Input:** owner-ranked complete candidates plus classification, duration, points, evidence and explicit favorite state.
- **Process:** preserve owner ordering; render the shared projection; open a candidate or accepted Instance by typed ID; distinguish candidate actions from immutable Instance actions; never accept or start implicitly.
- **Output:** a read-only browse-and-inspect path.
- **Example:** a 25-minute Focus Session shows TP/XP/BP, occurrence/support structure and evidence, then exposes `Accept`, `Modify` or `Back`; an accepted Instance exposes `Start Run` or `Create modified copy`.

#### 4. Manual Selection, acceptance and Modification

- **Input:** Mode, subtype, scope, context, timing constraints, a baseline candidate/Instance, supported edit commands and validation rules.
- **Process:** send intent to the resolution owner; receive a complete candidate; keep the baseline immutable; edit a transient proposal; revalidate after each edit; calculate exact signed TP/XP/BP deltas; accept only a complete valid proposal.
- **Output:** a new accepted Instance with its own typed ID and structure hash; the baseline remains unchanged.
- **Example:** removing an optional occurrence may change 30→24 minutes, TP 40→33, XP 18→16 and BP 4→4; the UI shows `−6`, `−7`, `−2`, `0`.

#### 5. Run — factual execution

- **Input:** accepted Instance, valid `runId`, exact occurrences/relations/bindings, lifecycle timestamps and persisted Run events.
- **Process:** restore Run state; derive the active occurrence from facts; render the real Chunk display; derive time from timestamps/monotonic deadline; append start/pause/resume/complete/skip/substitution events; never rewrite the accepted Instance.
- **Output:** resumable execution with an append-only factual history.
- **Example:** substituting Chunk B for accepted Chunk A appends a deviation containing `occurrenceId`, accepted Chunk, actual Chunk and reason; it does not edit the Instance.

#### 6. Finished — accepted versus actual

- **Input:** accepted projection, closed Run, realized timeline, deviations and actualizer-produced TP/XP/BP.
- **Process:** compare accepted and actual occurrences; show completed/skipped/shortened/substituted facts; show projected versus actual duration and points; hand longitudinal history to Stats.
- **Output:** an auditable completion summary.
- **Example:** accepted 30 min / TP40 / XP18 / BP4 versus actual 24 min / TP32 / XP16 / BP4, with substitution and shortening reasons. Never pro-rate rewards from elapsed percentage.

#### 7. Route convergence and legacy retirement

- **Input:** verified new screens, current routes/prototypes, compatibility needs and navigation tests.
- **Process:** add typed routes; point normal navigation to them; redirect legacy routes when needed; reject empty or timestamp-generated fake Instance IDs; prove workflow parity before archiving old screens.
- **Output:** `Recommendations → Details → Accept or Modify → Run → Finished`.
- **Example:** replace `/sequences/run` with empty Instance ID by `/sequences/runs/:runId`, which loads a real Run, its accepted Instance and event history.

### Settled conflicts that implementation must not reopen

1. Favorites means explicit saved/starred state, not “most done”.
2. Display `Free Time`; normalize legacy `Recharge` only on read.
3. Display `Mix It Up`; wire code remains `mixItUp`.
4. Start requires valid accepted Instance and Run IDs; no placeholders/timestamps.
5. Actual TP/XP/BP comes from the versioned actualizer, not elapsed-percentage proration.
6. Preserve occurrences, repetitions, roles, Bundle, Fusion, Parallel Layers and timing; never flatten to icon lists.
7. Finished centers accepted projection versus actual Run; account totals belong to Stats.
8. BP means Balance Points, never Bonus Points.
9. Every `LeelaChunkDisplay` receives owner-published facts for its exact binding.
10. Run timing derives from persisted timestamps or a monotonic deadline and reconciles after lifecycle resume.
11. Substitution appends a deviation event and preserves the accepted Instance.
12. Platform/activity strips are metadata; typed relations and `LeelaSequenceEnvelope` carry structure.

### Open aspects and safe defaults

1. Separate Play Mode landing versus direct Manual Selection: do not build an extra route first.
2. Dominant-versus-Mixed threshold: show per-occurrence symbols or `Mixed`; do not invent a threshold.
3. Notifications by platform: Run must remain correct without notifications.
4. Auto-advance versus confirmation: show declared ending policy; do not infer it from duration.
5. Prev/Next semantics: no silent completion; state changes append events.
6. Substitution alternatives: show only owner-returned feasible choices and reasons.
7. Sharing Finished: no functional Share CTA until Community/privacy owns it.
8. Feedback persistence: no saveable form without an owner-backed command/schema.

- Define identity display for friends, creators, cohort members, and other associated people under each privacy lens.
- Decide whether Community Referred affects Kharma ranking or remains a badge/filter/sort dimension only.
- Define Data, Query, and Ad settings and pre-action consent independently, including sensitivity, retention, reuse, tracking, visibility, frequency, and notifications.

UX/UI — vertical centring is unreliable and keeps being got wrong; needs a shared primitive

#148NewLIVE SNAPSHOT
＋

Native Priority: Normal · Type: Task

Implementation and acceptance evidence have not been independently verified. Native state is preserved.

Typed dependencies & relationships

No observed relation. Independence and execution readiness are not established.

Source description & acceptance evidence
## Problem

Text and glyphs repeatedly fail to sit on the **optical centre** of their container. This has now been corrected by hand on many elements and keeps recurring. Reading the code does not reveal it — the widget tree looks correctly centred — and the error is only visible in a rendered pixel capture.

## Root cause

Flutter centres the **line box**, not the ink. A `TextStyle` with no explicit `height` inherits the font's ascender/descender metrics, which are asymmetric around the glyph: digits and caps have no descenders, so the reserved descender space shifts the visible ink off centre. Any widget that centres a `Text` inside a fixed-height ring, pill or circle inherits that error.

## Measured evidence — Kharma card metric pills (2026-10-06)

Measured from a 420x1000 golden capture of `lib/features/kharma/kharma_mock_screen.dart`, all four pills (KP, TP, Referred, Fit) identical:

| State | Ring | Ink | Top gap | Bottom gap | Offset |
|---|---|---|---|---|---|
| Before | y=376..405 (h=30) | y=388..398 | 12 px | 7 px | **2.0 px below centre** |
| After strut fix | y=376..405 (h=30) | — | 6 px | 9 px | **1.5 px above centre** |

The fix applied was `StrutStyle(fontSize: 15, height: 1.0, leading: 0, forceStrutHeight: true)` plus `leadingDistribution: TextLeadingDistribution.even`. That made the result deterministic rather than font-dependent, but a ~1.5 px residual remains from cap-height vs ascent asymmetry.

## Why a one-off fix is not enough

- The correction has to be repeated at every call site that centres text in a shape.
- It cannot be verified by reading code; it needs a rendered capture and pixel measurement.
- Different font sizes in one line box (e.g. a 15 px figure beside a 12 px unit) change the result again.

## Proposed resolution

1. A canonical centring primitive in the design system — e.g. a `LeelaCenteredText` wrapper, or a shared `StrutStyle` exported beside `LeelaTypography` — so the correction exists once.
2. A golden-based check that asserts ink is centred within its container for the standard pill/circle shapes, so a regression is caught without a human eye.
3. Audit existing centred elements against it.

## Scope

General UX/UI, not Kharma-specific. Kharma is simply where it was measured; the same class of error is expected wherever text sits inside a ring, circle, badge or button.

## Insight (2026-09-29): WSL2 port reachability from Windows — read this before re-flagging a "port unreachable" issue

**Finding:** All 12 agent-facing service ports across both stacks (OpenProject/Firefly/Paperless/Nginx/Hermes-gateway/Hermes-dashboard × private+community) answered a `curl` from **Windows** (not WSL), even though most of them are still published as `127.0.0.1:{PORT}:...` in their compose files, not `0.0.0.0:{PORT}:...`.

**Why this matters:** an earlier finding (register ID R11, this same repo's `InstallationInsights.md`) diagnosed OpenProject's `ECONNREFUSED` as caused by WSL2 NAT never forwarding a `127.0.0.1`-bound container port to Windows, and fixed it by republishing that one port to `0.0.0.0`. It would be easy to over-generalize that into "every port must be republished to `0.0.0.0` to be Windows-reachable." **That generalization is false, and this test disproves it**: WSL2's default `localhostForwarding` relays `Windows localhost:PORT` → `the VM's own localhost:PORT` regardless of which local address the container's docker-proxy bound to *inside* the VM, for this native-WSL2-dockerd setup. So `0.0.0.0` was the correct fix for whatever OpenProject's specific problem was, but it is not a standing requirement for every service.

**Operational lesson, separate from the networking fact:** a first test pass here used a 3-second `curl` timeout and produced 2 false negatives (private Firefly `:8086`, community OpenProject `:9082`) — both were just slow to answer on a cold hit, not blocked. Retested at 8 seconds, both returned normally. **Before concluding any of these ports is broken, retest with a timeout of at least 8 seconds.** A short timeout looks identical to a real connection failure in a quick glance at exit codes.

**If a genuinely new port-reachability problem appears:** don't assume it's the same class as R11 without testing. Confirm with a `curl` from Windows at ≥8s timeout first; only if that still fails, apply the `0.0.0.0` republish used for OpenProject (`leela-op178/compose.shared-db.yaml`) as the template fix.
