# Antigravity Instruction Orchestrator

## Purpose

Write Antigravity instructions that make the intended target, execution mode, proof standard, scope, human gates, and stopping conditions difficult to misread. Optimize for real product participation and independently verifiable outcomes, not persuasive agent reports.

Read `references/lessons-learned.md` when diagnosing a failed or suspicious run. Read `references/prompt-patterns.md` when generating a new Antigravity prompt or handover.

## Core workflow

1. **Ground the task.** Identify repository, workspace root, branch, authoritative files, current verified state, dependencies, and the one bounded capability being changed.
2. **Classify the Antigravity job.** Choose one pattern: preflight, Teamwork plan-and-execute, bounded correction, real-product POC, post-verification hygiene, operational multi-module program, or independent audit.
3. **Name the real target.** State which actual product/library/application must participate at runtime and what exact supported interface proves participation.
4. **Define the anti-facade boundary.** List substitutes that do not count. If a named product cannot perform a capability, require `UNSUPPORTED`, `DEFERRED`, `BLOCKED_HUMAN_GATE`, or `FAIL` instead of a local imitation.
5. **Define independent proof before implementation.** Require a fixture/oracle/negative test that is not produced by the code under test. For external products, require evidence generated by the actual product.
6. **Choose the execution mode correctly.** Use Antigravity Teamwork `development` mode for repository/product implementation. Use a planning phase only when operator approval is required before execution. Never instruct a read-only/plan mode and simultaneously expect implementation.
7. **Bound scope and dependencies.** One module/correction at a time unless the user explicitly authorizes a program-level orchestration. A program may sequence modules, but each module still receives its own proof, verification, and commit.
8. **Design human gates.** For GUI login, OAuth, installer, DNS, Telegram, desktop app, or other operator-only actions, make Antigravity prepare everything first and request the smallest exact action.
9. **Require adversarial verification.** Verification must challenge the implementation rather than restate its report. Use failure injection, dependency denial, malformed input, mismatch fixtures, independent arithmetic, real product exports, or other external oracles.
10. **Stop deliberately.** Define whether the agent must stop after the plan, after a human gate, after one verified commit, or after a bounded module sequence. Never let it automatically continue into the next architectural module without authorization.

## Non-negotiable prompt elements

For implementation prompts, include these when relevant:

- Repository and exact workspace root.
- Exact branch and explicit prohibition on `main` mutation if applicable.
- Authority files to read.
- One exact target capability.
- Current failure being repaired.
- Real named product/library and required runtime crossing.
- Forbidden substitutes/facades.
- Independent oracle and negative/adversarial tests.
- Dependencies and out-of-scope modules.
- Official-doc freshness check before using install/config commands.
- Human-gate policy.
- Exact pass/limitation/fail states.
- Required evidence artifacts.
- Independent verifier invocation.
- Final task-state reset/clean working tree where used.
- Commit boundary and explicit STOP.

## Proof hierarchy

Prefer evidence in this order:

1. Actual external product/library runtime behavior.
2. Independent external or hand-computed oracle.
3. Failure injection proving no hidden fallback.
4. Product-generated export/backup/screenshot/tool output.
5. Deterministic subprocess/CLI receipts.
6. Code inspection.
7. Implementation-owned diagnostics.
8. Agent prose.

Never promote levels 7-8 into proof of levels 1-4.

## Anti-facade rules

Reject these patterns unless the user explicitly wants a local abstraction rather than product proof:

- Install product A but execute custom/SciPy/local code instead.
- Create a function named after an external API/MCP and call it product integration.
- Generate a local JSON/dict and call it a product backup/export.
- Copy the system-under-test output and call the copy an independent benchmark.
- Hard-code `BALANCED`, `OPTIMAL`, `network_disabled`, or similar success metadata and then test that same metadata.
- Claim a UI/product POC without launching or using the actual product.
- Directly modify private/internal product storage when a supported import/API exists.
- Recreate an unsupported product capability locally and describe it as supported.

## Verification design

Require at least one test that would fail if the named target were bypassed.

Examples:

- Patch/deny the library method and require hard failure with no fallback.
- Supply a deliberately wrong control ledger and require reconciliation mismatch.
- Block sockets during a local-only calculation instead of trusting `network_required=false` metadata.
- Compare product output to a separately maintained fixture rather than to a copy of itself.
- Import through the real desktop product and compare its exported values with the independent source fixture.

When a test only confirms a value the implementation itself writes, label it a self-check, not an independent oracle.

## Antigravity Teamwork pattern

For complex implementation:

1. Start a fresh Teamwork conversation.
2. Use `/teamwork-preview` with one bounded goal.
3. Select `development` integrity mode unless the task explicitly requires another supported mode.
4. Phase 1 must produce a reviewable plan/prompt artifact containing target, real interfaces, oracle, negative tests, scope, pass conditions, and human gates.
5. Stop for operator approval if the task is high-risk or the user requested approval.
6. Phase 2 may execute autonomously within the approved boundary.
7. Require Critic/Challenger/Auditor/Success Auditor or equivalent verification when available.
8. Require the independent product-proof verifier when configured.
9. Commit only the bounded module/correction.
10. Stop.

Do not use Teamwork as permission to combine unrelated modules into one uncontrolled run.

## Human-gate wording

Make Antigravity request the smallest operation-specific action.

Good:

> Open Wealthfolio, choose Import, select `C:\...\fixture.csv`, and send the import summary screenshot. Do not change any mapping manually unless the screen requires it.

Bad:

> Configure Wealthfolio and tell me when done.

The agent should prepare paths, files, values, expected screen/state, and required evidence before asking.

## Review an Antigravity report

Do not accept the report at face value. Verify the pushed repository or runtime evidence first.

Check:

1. Actual branch head and commit parentage.
2. Changed files versus claimed scope.
3. Real target import/call paths.
4. Tests and whether their oracle is independent.
5. Evidence artifacts and whether they are generated by the actual target.
6. Task/stop state returned to inactive if used.
7. Dependency readiness claims against the authoritative program file.
8. CI/runtime receipts if available.
9. Claims such as `OPTIMAL`, `offline`, `balanced`, `backup`, `MCP`, or `TradingView benchmark` for self-authored evidence.

Return one of:

- `PASS`
- `PASS_WITH_LIMITATIONS`
- `CORRECTION_REQUIRED`
- `BLOCKED_HUMAN_GATE`
- `FAIL`

State the smallest correction rather than reopening architecture when the core implementation is sound.

## Style selection

Use the shortest style that still carries the required controls:

- **Preflight prompt:** verify workspace customization/tool discovery only; no implementation.
- **Module launch prompt:** one correction/module, authority, target, proof, stop.
- **Teamwork prompt:** plan artifact first, then approved autonomous execution.
- **Post-verification hygiene prompt:** only narrow residual defects; explicitly preserve accepted architecture.
- **Real-product POC prompt:** product UI/API/export proof plus human gates; custom imitation forbidden.
- **Program handover:** sequence multiple dependent modules but retain per-module verification/commit boundaries.
- **Independent audit prompt:** read-only, compare claims to repository/runtime evidence.

See `references/prompt-patterns.md` for reusable skeletons.

## Default output when asked to create an Antigravity instruction

Provide:

1. A short statement of what the prompt is intended to accomplish.
2. One copy-paste-ready prompt in a fenced block.
3. Only the minimal operator instruction needed after pasting it, such as which Teamwork mode to choose or whether to return the plan for review.

Avoid long commentary after the copy-paste block unless the user requests rationale.
