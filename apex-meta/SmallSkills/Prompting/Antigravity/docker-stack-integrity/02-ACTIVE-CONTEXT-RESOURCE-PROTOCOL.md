# Active Context & Resource Protocol

## Purpose

Keep Antigravity accurate across a 13-module implementation program without allowing earlier modules, old architecture, or irrelevant repository history to pollute the active reasoning context.

## Active Context Envelope

For every major task/module, the active context may contain only:

1. `00-START-HERE.md`
2. `01-PROGRAM-ORCHESTRATOR.md`
3. this protocol
4. the single active module file
5. `apex-meta/Alpine/INTEGRITY-CORRECTION-STATE.md`
6. the exact target repository files named by the active module
7. current live runtime/Git evidence needed for that module
8. current official upstream documentation only when the module requires product/version/interface verification

Everything else is reference-on-demand, not mandatory context.

## Do not preload

Do not preload:

- all 13 module files;
- the full `ImplementationPlans/` directory;
- the full prior integration report unless the active module explicitly needs a claim from it;
- unrelated APEX/Hermes history;
- old chat transcripts;
- unrelated repositories;
- broad official documentation for products not involved in the active module;
- prior module command transcripts once their result file and state summary exist.

## Major-task context cycle

### A. Ground

At module start:

1. read current `main` head;
2. read compact program state;
3. load active module only;
4. fetch only its target files;
5. inspect live runtime only for named services;
6. if product semantics may have changed, check current official docs for that product only.

### B. Declare scope before mutation

Write a compact internal scope contract:

```text
module: MXX
claim_to_fix: <one sentence>
files_allowed: <exact paths>
runtime_allowed: <exact services/actions>
forbidden: <one-line exclusions>
proof: <positive + negative>
```

If actual state requires files/services outside the contract, expand scope only when necessary and record why in the result. Do not silently roam.

### C. Execute

Patch only the named defect. Keep unrelated cleanup out.

For research-heavy or verification-heavy work, use a fresh subagent/team member with only module-specific context. Do not give the verifier the implementation narrative as its primary evidence.

### D. Verify adversarially

Ask at least:

- Would this test still pass if the correction were absent?
- Is the observed result generated by the real target/runtime?
- Is a report/assertion merely repeating configuration intent?
- Did the module change anything outside its promised boundary?

### E. Persist and compress

Before leaving the module:

1. write `IntegrityResults/MXX-RESULT.md`;
2. update `INTEGRITY-CORRECTION-STATE.md` with only the compact fields defined by the orchestrator;
3. commit the bounded module;
4. record the actual pushed SHA;
5. discard detailed implementation context.

The next module should need only the state file, its own plan, target files, and specific predecessor evidence it explicitly names.

## Resource classification

### Global authority resources

- Antigravity instruction orchestrator skill
- Antigravity lessons learned
- Antigravity prompt patterns
- this correction program orchestrator/context protocol

### Runtime implementation resources

- `ki-basis/compose.yaml`
- `ki-basis/.env.example`
- `ki-basis/docker/nginx/default.conf`
- `ki-basis/docker/postgres/init/01-init-databases.sh`
- live Docker Compose/runtime state

### Documentation/evidence resources

- `apex-meta/Alpine/INTEGRATION-ACCEPTANCE-REPORT.md`
- `apex-meta/Alpine/ARCHITEKTUR-BASIS.md`
- `apex-meta/Alpine/ImplementationPlans/`
- `apex-meta/Alpine/IntegrityResults/`

### Sensitive resources

- real `.env`
- API tokens
- passwords
- application secret keys
- Hermes persisted credentials

Sensitive resources may be inspected locally when required, but values must never be copied into Git, module results, prompts, screenshots, or command transcripts committed to the repo.

## Context reset rule

A context reset is mandatory after every module commit. Carry forward only:

- module verdict;
- commit SHA;
- one-line consequential fact for downstream modules;
- blocker if any;
- next module ID.

Do not carry forward detailed code diffs, command logs, or reasoning once persisted in evidence.
