# ki-basis installation insights

**What this is.** One document, readable top to bottom, covering every wrong turn in building ki-basis: what
was tried, why it looked reasonable, why it broke, and the rule that prevents it next time. It merges the
git-commit history with evidence recovered from the operator's Downloads folder (patch bundles, correction
notes, and evidence files that were never committed). For a file-by-file map of sources, see
`OldPlans/INDEX.md` — but this file does not require reading that one.

**Current end state, for orientation.** One WSL2-native Docker engine ("Apex"), one shared PostgreSQL
cluster, private stack (`ki-basis`, port band 808x) and community stack (`lika-community`, port band 908x)
as separate Compose projects on that shared engine. Full current-truth detail: `ki-basis/docs/INFRASTRUCTURE.md`.
Everything below is how the project arrived there — and where it still has open cracks.

## 2. Ranked failure register

Ranked by **cost × preventability** — what most needs to not happen to the next installer.

| ID | Failure | Root cause | What was actually advised / built | Why it failed | Prevention rule |
|---|---|---|---|---|---|
| **R1 — CRITICAL** | Built the entire stack on Docker Desktop (Sep 1–7), then tore it out for a WSL2-native engine (Sep 26). | Which Docker host to use was never explicitly decided — the agent silently defaulted to continuity with the existing Ubuntu-WSL2 host, then the project drifted onto Docker Desktop instead without that being a deliberate choice either. | Full finalization program (9 modules), correction-patch bundles, and a gate script that **failed the build if the engine was WSL2** — actively guarding against the direction that turned out correct. | Docker Desktop's Hyper-V/LinuxKit VM is a **second RAM-hungry VM** on a shared-memory host. It eventually could not even allocate 8 GB and crashed outright — not a tuning problem, a ceiling. | Install on a WSL2-native `dockerd` ("Apex") from the start. Refuse to proceed (fail the script) if Docker Desktop is the active context — the same gate idea, pointed the other way. |
| **R1b — HIGH (co-critical with R1)** | The **9P filesystem bottleneck**: running DB/container state or git repos on the Windows drive through WSL2's 9P bridge (`/mnt/c`) caused 80–1400× slowdowns, 350% runaway CPU, unkillable D-state locks, and OpenProject `chown`/`fcntl` crash-loops. | State and repos were placed on `/mnt/c` instead of the VM's native filesystem. | An 8-file diagnosis-and-fix package (2026-08-25) — but its own first 6 modules carried **wrong file-count data**, corrected only in module 06. | The fix package itself needed a second, corrected pass before it was trustworthy — a smaller instance of the same "written down before verified" pattern. | All databases, container state, and git repos MUST live on native ext4 (e.g. `/var/lib/docker/volumes`, `/root/...`). Only read-only static config may bind from `/mnt/c`. Never run a database or git repo off `/mnt/c`. |
| **R2 — CRITICAL** | "Airtight" dual-instance isolation — two fully separate Postgres clusters, zero shared DB connections — was designed, then reversed to one shared cluster with per-tenant roles. | Isolation was treated as an absolute requirement instead of a tradeoff, which recreated a split the project had itself warned against and doubled the tuning/backup surface. | ADR-001 (§3.4: "no shared … database connections") and a two-Postgres runbook. | Running two full clusters cost real memory and operational surface for a guarantee (`REVOKE CONNECT` on a shared cluster) that a single cluster with per-tenant roles already provides. | One shared PostgreSQL cluster, per-tenant `priv_*`/`comm_*` databases and roles, `REVOKE CONNECT` for isolation. Do not stand up two clusters. |
| **R3 — HIGH** | Hermes containerization thrash: a single-container migration plus a containerd **downgrade** attempt failed; a much larger multi-repo orchestration epic was never authorized. | Container-runtime hacks (downgrades, nested containers) were tried before the Hermes runtime model itself was decided. | `HERMES-OPTION2-DOCKER-DOWNGRADE-PLAN`, the single-container Arch-3 migration runbook, the multi-repo v2 epic. | Fixing symptoms (crashes) with runtime hacks doesn't resolve an undecided architecture — it just adds more moving parts to something not yet settled. | Decide the Hermes runtime model first: one `hermes-agent` container, state on ext4 bind mounts (`/root/.hermes`, `/root/workspaces`), gateway mode. No downgrades, no nested containers. |
| **R4 — HIGH** | Copy-verbatim Compose blocks caused live incidents during the WSL2 cutover: an orphaned old `postgres` container also aliased `postgres`, so Firefly/OpenProject crash-looped against the wrong database; a retired OpenProject v14 instance was **resurrected** by a copied service block and crash-looped on an already-migrated schema. | Service blocks were reused without re-verifying container identity, and two things ended up sharing the same network alias (`postgres`). | The shared-DB compose file's OpenProject block, copied from the old compose file; the old local postgres left running. | A network alias is an identity claim. Copying a block doesn't copy the guarantee that the alias is unique — nobody re-checked. | Never run two containers aliased `postgres` on one network. Verify container identity before reusing any block. Reference OpenProject by its actual container name (`leela-op178-openproject`). Never `--remove-orphans` blindly on a mixed engine. |
| **R5 — HIGH** | Volume drift became a near data-loss incident: the checked-in compose file declared **named volumes** for Hermes while the live container actually ran on **bind mounts**; a plain `compose up` would have wiped ~7.9 GB. | The checked-in file drifted from what was actually running, and nobody re-applied it — old start-scripts stayed wired to the drifted file. | `ki-basis/compose.yaml` (drifted) plus `start-ki-basis.{sh,ps1}`. | A declared volume type is a promise about what `compose up` will do to existing data. When the promise stops matching reality, the next routine restart becomes destructive. | The declared volume type MUST match reality (bind mount for Hermes). Pin it explicitly. Add a pre-`up` check that compares mount type against the compose declaration before any restart. |
| **R6 — MEDIUM** | Community Hermes had a container data path bound into a OneDrive-synced folder (`.../OneDrive/.../call-agenda → /opt/data/call-agenda`). | A convenience mount pointed live container state at a cloud-sync layer. | The original community `compose.yaml`. | A cloud-sync client can rewrite, lock, or partially sync files underneath a running container — live state and cloud sync are two different consistency models sharing one path. | Never bind container state to a cloud-synced (OneDrive/Dropbox) path. Use ext4 named volumes. |
| **R7 — MEDIUM** | Restore very nearly failed during the cutover: `pgvector` (the `vector` extension) is not a "trusted" Postgres extension, so a role-scoped restore fails without a superuser pre-creating it first; separately, OpenProject's embedded PG17 dump needs a matching pg17 client (a pg16 client can't read it). | One uniform restore command was assumed to work for every database. | Implicit in the migration steps — no per-database restore branching was written down. | Different databases had different restore preconditions that a single generic restore procedure couldn't satisfy. | The restore step MUST pre-create `vector` as superuser before any role-scoped restore, and MUST match `pg_restore`'s major version to each dump's source Postgres version. |
| **R8 — MEDIUM** | The OpenClaw local-LLM executor was planned in detail, then found non-viable: the local 8B model lacked the needed capability, and the GPU crashed (Intel Arc 140V, Vulkan device-lost). | Betting on local-model execution on hardware that hadn't been validated for the workload. | The full OpenClaw local-executor implementation and install plan. | Capability and hardware suitability were assumed rather than checked before the architecture was built around them. | Do not include a local-LLM executor in the install. Hermes routes to hosted models; the install script omits OpenClaw entirely. |
| **R9 — MEDIUM** | Runbooks were repeatedly **hypothesised, then shipped, then corrected** after the fact: a "13-module integrity correction program" shipped the same day as the Sep 1 build; the DrvFs package carried wrong file-count data; multiple "documentation-truth correction" passes were needed; and — the same pattern one layer up — an OpenProject skill's "Preflight — DONE" status was written before 4 of its own 12 completion criteria had been checked (Sep 27), which is exactly what caused the live `ECONNREFUSED` failure two days later (R11). | Plans and status claims were written ahead of a real, observed run, and corrections were chased afterward instead of verification happening first. | The docker-stack-integrity correction program; the DrvFs package modules 00–05; the OpenProject "Preflight — DONE" note. | A written plan or status claim is not evidence. Every one of these had to be corrected only after someone actually ran the thing and it didn't match the claim. | An install script (or a "done" status) MUST be validated against a real end-to-end run, health-tested, before it is shipped or declared complete — at every layer, not only infrastructure. |
| **R10 — LOW** | Documentation scatter: at points there were 6+ overlapping "current" architecture docs, an agent-routing chain still pointing at the retired topology, and an inline secret left in a doc. | No single source of truth was enforced; superseded docs were left unbannered. | Multiple architecture docs across `apex-meta/Alpine/`, `ki-basis/docs/`, and elsewhere, without consistent supersession banners. | Readers (human or agent) had no reliable way to tell which document was current without checking dates and cross-references by hand. | One source of truth (`INFRASTRUCTURE.md`) plus one install script. Ship no competing runbooks; banner every superseded document. |
| **R11 — RESOLVED 2026-09-29 (network layer, fully re-audited)** | The OpenProject Windows-agent skill (`opCall.js`) could not reach OpenProject: `ECONNREFUSED 127.0.0.1:8083` from Windows. | The skill was built on the unverified assumption that a container port published to `127.0.0.1` **inside** the WSL2 VM is reachable from Windows the same way non-loopback ports are. It is not, for the specific port that was tested. | A compose-file comment asserted OpenProject was reachable at `127.0.0.1:8083` from both WSL2 and Windows; this was carried into a "Preflight — DONE" status and then into the skill build, never once tested as a `curl` from Windows. | WSL2's NAT networking does not forward loopback-bound container ports out of the VM for this specific case (confirmed via Microsoft's own docs and `microsoft/WSL#9515`). The claim "sounded" verified because it was written with confidence, not because anyone ran the check. | **Applied:** `leela-op178/compose.shared-db.yaml` now publishes `0.0.0.0:8083:80`. Live-verified: `opCall.js root`/`whoami` both return `200` from Windows. **Re-audit complete, not just applied:** all 12 agent-facing ports on both stacks (Firefly/Paperless/Nginx/Hermes gateway/Hermes dashboard × private+community) were curl-tested from Windows and all respond, even those still bound to `127.0.0.1` — WSL2's `localhostForwarding` relays regardless of internal bind address on this engine, so `0.0.0.0` was the right fix for this one case, not a rule to apply everywhere. Full writeup: `DUAL_INSTANCE_ARCHITECTURE.md` §6 addendum. |
| **R12 — LOW (process hygiene)** | Several chat-generated "correction" patch bundles for ki-basis were produced across sessions; none were ever applied to the repo. | Discussing a fix and applying a fix were never tracked as two different states — discussion was silently treated as adoption. | Each new session produced an internally consistent, plausible-looking patch bundle. | Bundles accumulated in Downloads faster than any were applied, until the operator had to state directly that none had landed — repo state and chat state had fully diverged. | Track every patch bundle's status explicitly: proposed / applied / superseded. Never assume a bundle discussed in chat changed the repo. |

## 3. Distilled install-script requirements

A correct first-time install of the current architecture should, in order:

1. **Engine gate.** Use WSL2-native `dockerd` ("Apex", Ubuntu) only. Fail the script if Docker Desktop is the active context. (R1)
2. **Filesystem gate.** All DB/container state and git repos on native ext4. Fail the script if any of them resolve under `/mnt/c`. (R1b)
3. **Shared DB first.** Create `shared-db-net`; bring up one PostgreSQL 16 + pgvector cluster; create `priv_*`/`comm_*` databases and roles; `REVOKE CONNECT` cross-tenant. Pre-create the `vector` extension as superuser before any restore. (R2, R7)
4. **Private stack** (`-p ki-basis`): valkey/firefly/paperless/nginx/hermes, with Hermes on ext4 **bind mounts** (`/root/.hermes`, `/root/workspaces`) — declared volume type must match this exactly. (R3, R5)
5. **Community stack** (separate repo `lika-community`, `-p community`): named volumes only, never a cloud-synced bind path. (R6)
6. **OpenProject:** fresh install (currently 17.8, `leela-op178`) on both `shared-db-net` and `ki-basis-net`; reference it **by container name**, never revive a retired version via a copied block. (R4)
7. **Port publishing, decided once for every service:** publish every Windows-agent-facing port to `0.0.0.0` inside WSL2. Verify each with a `curl` from Windows before calling anything reachable. (R11)
8. **Exclusions:** no Docker Desktop, no second Postgres cluster, no single-container/downgrade Hermes hacks, no OneDrive binds, no local-LLM executor, no blind `--remove-orphans` on a mixed engine. (R1–R8)
9. **Memory:** size `.wslconfig` / per-service Compose limits against **measured commit under real load**, not container RSS and not a prior engine's tuning numbers. Keepalive so the VM doesn't idle-sleep. (R1 performance evidence)
10. **Verify, don't assume.** Run the real health test at the end; the script is "done" only when it is green — apply this to skill/application-layer "done" claims too, not only infrastructure. (R9, R11)
